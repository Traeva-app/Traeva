## 1. Shared files and how they are integrated

**Common flow**: each lane includes its **minimal, bounded** changes to shared files in its own PR and lists them one by one in the "Shared file changes" section of the PR description; Claude-A checks them in a PR comment (adjusting numbers, dependency versions or registration order before the merge when needed); the student merges. No agent merges. The two items below are exceptions:

- `Cargo.lock` / `package-lock.json`: may be updated on your own branch during development; before the merge, A regenerates them from the approved dependencies and checks the diff, instead of taking ours/theirs wholesale.
- Migration numbers: the numbers in each lane's PR are only provisional; A assigns the number before the merge (see §3).

Within a currently assigned implementation scope, the following technical patterns apply:

- `impl OrganizeService { ... }`: the feature's public methods (`analysis.rs` already does this). Adding a new `OrganizeService` field (background thread, queue, etc.) is a shared change to `lib.rs`.
- `impl Store { ... }`: the feature's own SQL, using `connection()`, `sqlite_error()`, `to_json()` provided by `store.rs`. The lock of `connection()` is held only during short database operations, never across file operations or network waits.
  - Write only to the tables your own migrations created.
  - You may only read (SELECT) `files` and `snapshots` (for example listing files that have snapshots, finding adjacent snapshots not yet analyzed); you must not write them.
  - Snapshot bytes and text are obtained only through `read_snapshot` / `snapshot_text`.

A new module's change to `lib.rs` is usually only two lines: `mod <module>;`, and `pub use` when needed.

## 3. Specific rules for shared changes

- **Migrations**: a new table or schema change is written as a new file `crates/traeva-core/migrations/NNNN_<topic>.sql`. During development use the next free number on main at that time; A assigns the number before the merge, and on a collision A renumbers and updates `MIGRATIONS` and the tests in §1 that change with migrations. A committed migration is never modified. Every migration is tested on an empty database and on an upgrade from the previous version's old database. Memory/Source tables use foreign keys only to `files(file_id)`, `snapshots(snapshot_id)` and the tables created by the lane's own migrations (#31's tables reference #32's `memory_watches`), and do not change the seven Organize tables.
- **Dependencies**: a new crate (for example D's zip/XML parsing) is stated in the PR with its name, version, purpose and `default-features` choice; A checks it and then updates the manifest and lockfile for all lanes.
- **Commands**: the implementation of a new Tauri command goes in the lane's own `*_commands.rs`; the name is added in three places at once: `command_names.rs`, the `lib.rs` handler and `capabilities/main-window.json` (a shared change, checked by A). No fs/sql/shell or other plugin permissions are added.
- **Errors**: reading snapshots uses `stage: memory` (§5). When another feature needs a new `ErrorCode` or `ErrorStage`, propose it as a shared change to `contracts.rs`: append only, do not change existing values, and update `src/features/organize/types.ts` to match.
- **Frontend type mirrors**: the Rust types returned by new commands are mirrored by hand by that lane in its own `src/features/<feature>/types.ts`; `AppError` is mirrored only once, in `src/features/organize/types.ts`, and other pages import it from there.
- **New listening ports, browser extension communication, permission or CSP changes**: first state the purpose and the isolation method in #65 or the lane's Issue; A checks, R re-verifies; off by default.

## 4. Data contracts

### 4.1 FileRecord (`files.file_id`)

- One `file_id` corresponds to only one physical object; **the reverse does not hold**: the same physical object may have several `files` records. Continuity comes only from direct observation and this app's own operations (organize-spec.md §2.3).
- Physical evidence (dev, inode, birth time) is only evidence, not identity. The same hash, the same name or the same title can **never** merge two `file_id`s.
- **Volume identity (v46)**: `dev` (`st_dev`) is valid only while the volume is mounted: after a restart the same volume may get a different number, and after one disk is ejected, the next disk attached may get the same number. Found on 2026-10-15: after one shutdown and restart, macOS gave the data volume a different number (R's test database recorded 16777232 on 10/11–10/12; the same folders with the same inodes are now 16777234). As a result every authorized root reported `root_changed`, and Undo, recovery, Memory's capture/relocation/automatic linking, Source and export all treated the same object as "another object". organize-spec §3 calls this "volume/object identifiers", which are only evidence, so this is an implementation fix; the frozen spec does not change.
  - The saved evidence JSON gains an optional field `volume`: the volume's UUID, 32 lowercase hexadecimal characters. It is used in `FileEvidence` (`files.observation_json`, `snapshots.observation_json`, `path_history.evidence_json`, `plans.expected_source_json`, `actions.preconditions_json`, the move records in the execution log `action_events.detail_json`, the `evidence_json` of the three Source tables), `RootEvidence` (`authorized_roots.evidence_json`), `ChainLink` (the folder chains in `plans.folder_chain_json` and `expected_source_json`) and the execution log's `FolderReceipt`. If the UUID cannot be read, the field is not written. `dev` is still written into the JSON, for diagnostics only. No migration: old records have no `volume` and are read as before.
  - Where the UUID comes from (`platform::macos::volume_uuid`): use `getfsstat` to find the mount point whose `f_fsid.val[0]` equals this `dev`, then call `getattrlist(ATTR_VOL_INFO | ATTR_VOL_UUID)` on that mount point. Only the `dev` just observed is used for the lookup, never a saved one. No caching: during the review it was seen on this Mac that after ejecting one disk image and attaching another, the two got the same `st_dev` and different UUIDs; caching by `dev` would store the old disk's UUID in new records. Each lookup is one `getfsstat` plus one `getattrlist`. It is the Volume UUID that `diskutil info` shows.
  - Comparison rules (`FileEvidence::same_object`, `RootEvidence::same_object`, `ChainLink::same_folder`): the same inode, the same birth time (folder chains have no birth time; compare name and inode), and the same volume: when both sides have `volume`, they must be equal; when one side has none (saved before v46, or could not be read), the volume is not compared. **A saved `dev` is never compared with later observations.** Two live values within the same run are still compared directly by `dev` (whether two roots are on the same volume, whether a file is on the root's volume, whether what is confirmed after a move is the object just moved).
  - "Unchanged" (`FileEvidence::same_state`): the same object by the rules above (comparing the volume when both sides have `volume`), and the same mtime, ctime and link count. A changed `dev`, or an old record gaining `volume` this time, does not count as a change, so observing the same file again after a restart does not increment `record_revision` and Memory does not reread because of it; the new observation (with `volume`) is written back to `observation_json` as usual.
  - Old records need no reauthorization: roots and files saved before v46 are recognized by inode and birth time even when a restart changed the number. The `dev` in page tokens (export, relocation, association, the pending-confirmation page) is unchanged: tokens are only compared within the same run, and pages fetch again after a restart.
  - Records with `volume` cannot be read by programs before v46 (`deny_unknown_fields`). A data directory that has been opened with the new version can no longer be opened with an old version (reading `saved_roots` at startup reports `DatabaseCorrupt`). Verification uses only copies of app-data, and never opens them with old release candidates.
- The current registration rule (`record_observation` in `store.rs`) compares only with `present` records at the **same path**:
  - Same path, same object: keep the original `file_id`; if the content changed, increment `record_revision`.
  - Same path, another object (replaced): the old record becomes `missing`, and the new object gets a new `file_id`. This happens only when the path is observed again.
  - A file renamed or moved outside Traeva and then registered at the new path: it gets a **new** `file_id`; the old record at the old path is still `present`.
  - A **failed** observation (for example there is no file at the old path any more, returning `file_not_found`) writes nothing: the old record does not become `missing` because of it. Only when another object is **successfully** observed at the same path does the "replaced" branch above apply.
  - So `present` is only the state at the most recent successful observation and cannot be taken as evidence that "the file is still in place now"; a `present` record found by path may be out of date, and the result of this observation is what counts.
  - #31 does not change these rules: objects obtained through candidate capture (§4.2b, M1b) and the user's manual relocation (M2) are registered by the same rules: they usually get a new `file_id`; on relocation, if that path already has a registration Organize made for the same object that has no Memory record yet, that one is reused. To write the registration and the candidate snapshot in the same transaction, the transaction body of `record_observation` was extracted into `observe_in` in `store.rs` (v10); `record_observation` is just "begin a transaction, `observe_in`, commit", with unchanged behavior. Neither candidate registration nor relocation registration triggers Source's `continue_registered_sources` (that step belongs only to Organize's `register_file`, §4.5), so the source association stays on the old `file_id`. Relocation also marks the old file record `missing` (its object was found at the new place and has only one name), the same as Organize's own move (`record_move`). Their continuity with the original work is recorded only in #31's relations (§4.3); `file_id`s are not merged.
- **Measured (2026-10-08, APFS on this machine)**: Foundation's atomic write (`write(atomically: true)`) and `FileManager.replaceItemAt` (the method NSDocument-style apps use for "safe save") give the path a new inode every time; only in-place writes keep the inode. So when saving with such editors, every save gets a new `file_id` under the current rules. Whether and how these `file_id`s are linked into the same work is decided by #31's student rules. The saving methods of specific apps such as TextEdit and Word are measured and recorded by #32.
- Only core writes `files` and `path_history`: Organize's registration (`record_observation`), the commits of execution, Undo and recovery (`record_move`, through `commit_move` / `commit_recovered_move`), and #32's capture. Other lanes only read and only reference these with foreign keys; they do not create or modify file records with SQL.
- User files can be read only through core: inside an authorized root, opened level by level by fd, read stably. The rule of zero writes inside a root before confirmation applies to Memory/Source too: no file writes, no extended attributes, no hidden metadata.

### 4.2 Snapshot (`SnapshotRef`) and the read-only consumption boundary

Fields of `SnapshotRef` (the JSON name is the field name, fixed by tests):

| Field | Meaning |
|---|---|
| `snapshot_id` | UUID |
| `file_id` | The FileRecord these bytes were read from |
| `sequence` | 1, 2, 3… in capture order under this `file_id` |
| `file_revision` | `files.record_revision` at capture time |
| `root_id`, `relative_path` | Where the file was at capture time |
| `sha256`, `byte_length` | SHA-256 (lowercase hex) and length of the exact bytes |
| `captured_at_ms` | Capture time (Unix milliseconds) |

Rules:

- A snapshot only means "the file did not change between two complete reads"; it **does not mean the writer has finished saving**.
- When a new read of the same `file_id` has the same SHA-256 as its latest snapshot, no new snapshot is created. So two adjacent snapshots under the same `file_id` always have different bytes.
- Snapshots are immutable: not changed, not replaced, not repaired, and not deleted in the CAC stage either (the retention and cleanup policy comes after CAC).
- The bytes are stored in app-data at `snapshots/<first two chars of SHA-256>/<SHA-256>`: first written into `snapshots/incoming/`, F_FULLFSYNC, read back and checked, then renamed into place without overwriting and the directory fsynced, and only then is the `snapshots` table written. Snapshots with the same bytes share one copy. These directories are opened level by level from app-data without following symbolic links. Other lanes **do not open this directory directly**; they read only through core; every read checks the length and SHA-256 again.
- After a copy goes missing, it reappears only when bytes with exactly the same SHA-256 are captured again; no other content ever takes its place.
- Table name `snapshots`, primary key `snapshot_id`, created by `0002_snapshots.sql`; other lanes' migrations may reference it with foreign keys. Rows cannot be changed or deleted (triggers).

Capture happens only when Memory is enabled for a file (§4.2a); core offers no "capture any file" interface (v3's `capture_snapshot` became test-only in v4). Other lanes' tests that need snapshots use `start_memory` / `check_memory`. The rules of each capture:

- Only the **same physical file** is captured. When the original path has been replaced by another object, it returns `file_changed` and records nothing. The only exception is candidate capture the user enabled for this record (§4.2b, implemented in v11); even then, the new object is only a candidate, not a version of the original file.
- Recording the observation and inserting the snapshot happen in the same transaction, after first checking: the watch is still on, the authorization is still valid, and the file record is still the one from when the capture started (present, same place, same object, same revision number). If the file is re-registered or changed during the capture, it returns `file_changing`; if the authorization was revoked, it returns `root_revoked`; in both cases nothing is written (a harmless unreferenced copy may be left behind).
- No object at the recorded place returns `file_not_found`; another object at the place returns `file_changed`, and **first looks only at metadata, without reading that object's content** (v10: look once inside the execution lock before reading; check once more after reading, to guard against a swap in between). In automatic capture (`check_memory`), if the record is already `missing` and there is an object at the place, it also reports `file_changed` (since v10; before that, `file_not_found`); when enabling Memory with the record already `missing`, it still reports `file_not_found`. Revoked authorization returns `root_revoked` and nothing more is read; a file with an unresolved action returns `unresolved_action`.
- Capture and the executor's move share the same lock and never run at the same time. Capture only reads files inside a root; zero writes inside the root.

Read-only interface (implemented). `list_snapshots` returns `unknown_file` for a `file_id` that is not registered; for a file that is registered but has no snapshots yet it returns an empty list; the two are not confused.

```rust
impl OrganizeService {

    pub fn list_snapshots(&self, file_id: &str) -> Result<Vec<SnapshotRef>, AppError>;
    /// The exact bytes, with SHA-256 checked.
```

### 4.2a Per-file opt-in automatic capture (#32, the student's decision 2026-10-08)

Memory records automatically only for the one file the user **explicitly enabled**; other files, including files in the same folder, editors' temporary files and newly appearing files, are never captured. There is no folder-level batch Memory.

```rust
impl OrganizeService {
    /// Enables Memory for a registered file and saves the first version right away; when already enabled, returns the same watch.
    pub fn start_memory(&self, file_id: &str) -> Result<MemoryWatchView, AppError>;
    /// Stops Memory: no new versions after this; saved versions are kept. Returns None if it was never enabled.
    pub fn stop_memory(&self, file_id: &str) -> Result<Option<MemoryWatchView>, AppError>;
    /// All watches: active ones first, then stopped ones (most recent first, at most 200).
    pub fn memory_watches(&self) -> Result<Vec<MemoryWatchView>, AppError>;
    /// (v10) All watches of one file, oldest to newest, no limit on count; and the gaps related to them (§4.3a).
    pub fn memory_watches_of(&self, file_id: &str) -> Result<FileWatchesView, AppError>;
    /// One round of watching: the desktop app's background thread calls it about every 2 seconds (MEMORY_CHECK_INTERVAL).
    pub fn check_memory(&self) -> Result<Vec<WatchCheck>, AppError>;
}
```

- `MemoryWatchView`: `watch_id`, `file_id`, `status` (`active` / `stopped`), the current place in the record (`root_id`, `relative_path`), `started_at_ms`, `stopped_at_ms`, the number of saved versions `versions`, the latest snapshot `latest`, the time of the last look in this run `checked_at_ms` and that look's problem `problem` (`AppError` or null, kept only in memory, empty after a restart).
- `WatchCheck.outcome` (distinguished by `kind` in JSON): `unchanged` (file not read), `saved` (new version), `same_bytes` (saved again, but the bytes are the same, so no new version), `problem` (with `error`), `stopped` (the watch is stopped, nothing saved); v11 adds `candidate_saved` (with `snapshot`, `candidate_id`: the object at the place was saved as a candidate, nothing confirmed) and `candidate_paused` (the candidate quota is full, nothing read); v45 adds `linked_automatically` (with `snapshot`: the new object at the place was automatically recorded as the next version and the record moved to the new file, see §4.2b). This row still hangs on the old watch, and the problem left by the old watch's last look is cleared along with it.
- How changes are found: each round only looks at the file's metadata through the root handle, without reading the content. A capture happens (read and check; no new version if the bytes did not change) only if any of the following holds:
  - The physical evidence (including mtime, ctime, link count) or the size differs from the file record. ctime changes with every write, so a change where "the size is the same and mtime was restored" is also found;
  - The file has no snapshot yet, or the SHA-256 in the file record is not the latest snapshot's (for example the file was chosen again on the Organize page, or the first capture on enabling failed). This item only queries the database.
- Several saves in a row between two rounds record only the last state; there is no claim that every save is captured. The background reads a file at most once per round (two reads with a pause in between); if the file is still changing, it tries again next round, and does not hold the execution lock for long.
- Startup catch-up check: after a restart, the first round of checks finds changes made while Traeva was closed, by the rules above. The period when Traeva was not running is itself recorded as a gap (§4.3a), even if the content did not change after the restart.
- (v10) Every watch belongs to a record chain (§4.3a): `start_memory` creates or reopens the record chain and the work; `stop_memory` stops it together with the record chain. After the record has continued onto another file, stop it by record chain (`stop_memory_record`); calling `stop_memory` with the old file only returns that long-stopped watch and does not affect the new file being recorded.
- **No following, no associating**: a file renamed or moved outside Traeva reports `file_not_found`; it is only reported, not captured. The approach #31's material set: for external renames and moves, the user manually picks the new place, and core continues only after checking that it is the same physical object; the system does not search by itself (implemented in v12, §4.3a manual relocation). The original path replaced by another object (replacement save): since v45 it is first handled by §4.2b's "replacement saves linked automatically" (the student's decision 10/14, exact place only); only when it cannot be linked does it report `file_changed` as before, and it is saved as a candidate when candidate capture is on. Moves Traeva makes itself (Organize, Undo) belong to the file record itself, and Memory follows the file to the new place.
- Stopping is final: once a watch is stopped it never reopens; enabling again creates a new watch. `stop_memory` first waits for an in-progress capture to finish (the same execution lock); after it returns, no more bytes of this file are read or saved; the transaction that saves a snapshot also checks once more that the watch is still on.
- Database: the `memory_watches` table (`0003_memory_watches.sql`), at most one `active` per file at a time; rows are not deleted, only `status` and `stopped_at_ms` change.
- The window commands are in `family_commands.rs` (v10, §4.3a); the UI is done by B in #35; the desktop app already runs `check_memory` in the background.

Until these interfaces are merged into main, B and D develop with pure functions: the input is a `TextExtraction` or bytes, with no dependency on the database.

### 4.2b Candidate capture after replacement (#31 material section 3, implemented in v11, `candidates.rs`)

Below are the constraints #31's material places on capture; v11 implemented them as written. Since v45, a replacement is first handled by "replacement saves linked automatically" below, and goes through the rules here only when it cannot be linked. When candidate capture is off, a replacement that cannot be linked is only reported (§4.2a), and a `replaced_uncaptured` gap is recorded (§4.3a).

- **Replacement saves linked automatically (v45, `auto_link.rs`; the student's decision 10/14, changing #31 material's rule "do not associate files by path or name", for this one case only)**: editors such as TextEdit and Word save by first writing a new file and then swapping it to the original name, so every save leaves a new file object (new inode) at the same path. For an open record, a new object that appears at the **exact place** (same authorized folder, same relative path) is automatically recorded as the next version of the same work: no card, no question to the user; the UI labels it "Linked automatically", and the user can undo it (§4.3a correcting a relation). A file renamed or moved elsewhere still needs manual relocation; that does not change.
  - Scope: every open Memory record; no new switch. It is tried only for a "new object" at the place (defined as for candidates below: no snapshots, no open watch, not in any work), before candidate capture. When the place holds a waiting candidate, an already decided file, or another record's file, things are as before.
  - Preconditions (if any fails, the earlier rules apply): the execution lock is held; the watch is still the one open on the record chain (the record is not stopped, not lost, not paused); there is no unresolved Organize operation in the authorized folder; the folder is still valid; the read the watch makes (`WATCH_READ`) still stably reads the object that was seen. Then in **one transaction** check again that the watch, the authorization and the record at the place are still the ones from the look, and compute the parent version of "continue" by the same rules as the pending-confirmation page: it must continue exactly from the latest version on the record line (`unread_continue` is `(Some(parent_version), 0, None)`: no earlier candidate is waiting, and it does not skip over an object the user put off the line; #31's intermediate-object rule: a relation that skips over such an object can be created only after the user has looked at it).
  - Failure: still being written (`file_changing`), or replaced again during the read: nothing is written, no gap is recorded, and it retries next round. Persistent refusals (over 20 MiB, hidden, hard link, symbolic link, not downloaded, another volume) and refusals inside the transaction (stopped, not a new object, place changed) are all handled as before: report `file_changed`, record a `replaced_uncaptured` gap, and the pending-confirmation page shows it; when candidate capture is on, it is saved as a candidate as before (what cannot be read still cannot be read, and `capture_failed` is recorded). Every round tries the automatic link again, so versions saved normally later are still linked; that snapshot pair carries this gap. A refusal inside the transaction happens after the read: the bytes read are already stored in app-data's snapshot directory, but no snapshot row points to them (the same order as a normal capture; not a version, and never sent).
  - How it is written (one transaction, sharing `continue_current_in` in `family_decide.rs` with the user choosing "continue" on the pending-confirmation page, so the two cannot drift apart): register the new object by Organize's rules (new `file_id`, the old record becomes `missing`) and save its first snapshot; one `memory_decisions` row (`continue`, with the parent version, `candidate_id` empty, `page_token` being the page token computed in the transaction: a `continued` watch link requires a decision); member `confirmed_system`, basis `user_decision` (0007's list of bases cannot be extended; the basis is shown only in the work view and no code branches on it; whether something was linked automatically is read from the table below); relation `continuation`, `confirmed_system`, `skipped_items` 0; the record chain's latest version moves forward; if there is an unfinished `replaced_uncaptured` gap, it ends with `captured`; if there is none, **no gap is recorded** (Traeva saw this save; otherwise every replacement save would show a gap); `move_watch_in(…, continued)`: the old watch stops, and the new watch opens on the new file, on the same record chain; finally one row is written in `memory_auto_links` (migration 0012), marking that this relation was linked by Traeva itself. **It does not write `memory_candidates` and uses no candidate quota** (the limit of 20 counts only candidates). The user's own "continue" is as before: it writes a candidate row (`read_on_decision`) and `confirmed_user`, and when there is no gap it adds an already-ended gap.
  - This round's result is `linked_automatically`, which counts as saving a new version. The sending permission is still that of the record line's first file (`permission_file_ids`), so this file's Memory agreement also covers the automatically linked versions.
  - `memory_auto_links`: `edge_id` (primary key), `member_id`, `chain_id`, `decision_id` (unique), `linked_at_ms`; append-only, never changed or deleted. After an undo this row is still there and the relation becomes `superseded`; it is also still there when the user later confirms again (`confirm_again`, the relation becomes `confirmed_user`). So `VersionRelationView.linked_automatically` says who made the link and is always true; `VersionPairView.linked_automatically` is true only while the relation is still `confirmed_system`, so a pair the user has confirmed no longer shows "Linked automatically" or undo.

- **Switch**: explicitly enabled per file (per record task), off by default; existing watches do not get it automatically. Before enabling, four points must be explained:
  - The scope is only the exact place this file is currently bound to;
  - A new object may be the result of an editor's save, or an unrelated file;
  - Candidate content is stored in the local app-data and cannot be deleted in the CAC stage;
  - Saving a candidate does not mean confirming that it belongs to the original work.
- **Off**: the same as §4.2a: only `file_changed` is reported, and the new object's body is not read. Only after the user confirms and authorizes continuing does recording continue from the object present at that time; intermediate versions not captured before cannot be recovered.
- **On**: when the recorded place is taken by a new object:
  1. Check the authorization and directory chain, and read stably;
  2. Register a new `file_id` by the rules of `record_observation` (`observe_in`, §4.1) (the old record becomes `missing`), and save a real snapshot in the same transaction;
  3. Mark it as a candidate and put it in this record task's pending-confirmation group.

  Only this exact place: other files in the same folder and editors' temporary files are never captured.
- **Limits**: each record task has at most 20 unprocessed candidate objects and 20 unprocessed candidate snapshots; when either is reached, candidate capture pauses.
  - The quota is counted over the whole continuous record task (the continuation chain): watch continuation, new candidate groups, restarts and repeated notifications do not reset the quota; "not sure yet" does not release quota either. Processing a candidate releases the corresponding quota; saved snapshots are not deleted because of it (confirmed by the student 2026-10-08, [record](https://github.com/P30g53/Traeva/issues/65#issuecomment-6075146682)).
  - The paused state is persisted. While paused: no reading, no saving, no queueing.
  - On resuming, only the state actually present at that time is captured, and this gap is recorded in the history.
- **Stop**: when Memory is stopped, the authorization is revoked, or the current object is judged independent, candidate capture stops and does not resume automatically.
- **Implementation notes (v11)**:
  - The switch is an "enabled period" row (`memory_candidate_switches`); turning it off is final, and turning it on again creates a new row. Enabling must carry the `notice_version` the page showed (core's `CANDIDATE_NOTICE_VERSION`, incremented whenever the four points of the notice change), otherwise `page_outdated`. Since v18 it must also carry the `place_token` the page showed: the permission applies only to the place written in the notice. If the file was moved away after the notice was shown (by Organize, Undo or relocation), or the request does not carry the token, `page_outdated` is returned, nothing is written, and the page must reread the notice (an issue C found in #37, [#65 issuecomment-6102864317](https://github.com/P30g53/Traeva/issues/65#issuecomment-6102864317)).
  - Enabling only after the replacement (D2): the page's `unread_occupant.occupant_token` stands only for the object shown at that time (and for "whether it will be saved right away"). If the object at the place has changed at enabling time, `page_outdated` is returned and nothing is written; if not, it is read and saved as the first candidate in the same step (reason `present_when_enabled`); if the read fails, the error is returned as is and the switch stays off. When `saves_occupant_now` is true, the enabling notice must state "this authorization includes the object that has currently replaced the file".
  - A candidate can only be a "new object": no snapshots, no open watch, not in any work. Files of other records and files judged unrelated are only reported, not read.
  - Everything one capture writes (file record, snapshot, candidate, membership, quota, gap) is in the same transaction, and the transaction checks again that the watch is still on, the switch is still the same period, the authorization is still valid, and the record at the place is still the one from before the read.
  - The quota is computed fresh every time: this record's number of unprocessed candidate objects and their number of snapshots. On reaching 20 a `paused` gap is recorded; when processing candidates brings the number below 20, the gap ends with `released`, and the next round captures only the object present at that time.
- **What candidate snapshots mean to other lanes**: they are ordinary `snapshots` rows (never changed, never deleted), marked as candidates only in #31's relations. **Other lanes must not treat a candidate object's snapshot as a version of the work**: no analysis, no retrieval, no sending. Whether a snapshot can be used is always decided by the core judgment of §4.3.

### 4.3 Version order and family (#31 material Accepted; M1a has implemented usable snapshot pairs)

The rules follow [#31's material](https://github.com/P30g53/Traeva/issues/31#issuecomment-6074393105). Below is the part other lanes depend on.


- Only two kinds are usable, and both need positive evidence:
  - Two snapshots with `sequence` n and n+1 under a **confirmed member file** of a work (`confirmed_system` / `confirmed_user`);
  - Two snapshots connected by a confirmed relation (continue or branch) whose two ends are both confirmed members (produced by decisions since v11).
- The snapshots of candidate objects, files judged unrelated and unconfirmed relations **never appear**. A file not in any work (Memory never enabled) has no usable pairs either.
- Fields of `UsablePair` (the JSON name is the field name, fixed by `lineage_tests.rs`):
  - `before`, `after`: two `SnapshotRef`s;
  - `basis`: `same_file`, `continuation` or `branch`;
  - `evidence`: `system` or `user` (a relation or membership the user confirmed); a user confirmation is not upgraded to system evidence;
  - `gap` and `gap_kinds`: Memory may not have seen every save in between, so it can only say "these two versions differ", never describe it as one save. `gap_kinds` lists every recorded reason:
    - Gaps that start from `before` (§4.3a's `memory_off`, `paused`, `capture_failed`, `replaced_uncaptured`, `lost`, however they ended later);
    - The watcher was not running between the two versions (`watcher_stopped`), or the time is before any run record exists (`not_recorded`, data from before 0007);
    - Skipping over an object that is not on this line, or a branch whose starting point is not the version at which it was found, or a relation created when the user "associated it with a work" (`skipped`, v15: Memory did not see what happened between the two versions); a relation that skips over an object also carries the gaps that started before the skipped object;
  - `unplaced`: this file's position in the work's order is unknown ("same work, order unknown"). It may be shown and compared, but #34 must not use it for ordering or for finding "first / last";
  - `family_id`; `chain_id`: the record chain of the line `after` is on; null when it is not on any record chain's line;
  - `permission_file_ids`: before sending this pair's lines, the Memory sending permission (`memory_consents`) of **every one** of these files must be valid (D4). A pair on the same line has only one (the record chain's first file; v17: after the line is cut by an undone continuation, the first file of this segment); a pair of a cross-file relation (a branch, and since v17 also a continue across two lines) contains lines from both sides, and the permissions of both sides are needed;
  - `edge_id`: the relation it is based on; null for two versions of the same file.
- `PairCheck`: `{"state":"usable","pair":…}` or `{"state":"not_usable","reason":…}`; the reasons are `not_a_member`, `candidate_version`, `no_confirmed_relation`, `not_adjacent`, and v17 adds `relation_disputed` (the relation between these two versions is disputed, use paused) and `relation_superseded` (the relation has been undone or replaced). An invalid ID returns `invalid_input` with `stage: memory`; a snapshot that does not exist returns `unknown_snapshot`.
- No lane **pairs snapshots of different `file_id`s into before/after versions on its own**, and no lane saves family IDs it made up.
- **After works are merged (v14)**: the `family_id` in snapshot pairs and records is the current work (live work) and changes after a merge, so **do not save it and do not use it as a key**. Old work IDs remain valid, and any function given an old ID treats it as the current work. Each pair appears only once in `all_usable_pairs`. A merge does not infer an order between the versions of the two works: after the merge, there are no snapshot pairs between versions that came from different sides. For files merged in, the `evidence` of their snapshot pairs is `user`: they belong to this work because of the user's merge decision (material section 6: a user confirmation is not upgraded to system evidence).
- Editors that save by replacement (TextEdit, Word, etc., §4.1) produced no usable cross-file pairs before M1b. Since v45 each of their saves is automatically linked as a continue relation (§4.2b), so there are usable cross-file pairs: `basis` `continuation`, `evidence` `system`, `edge_id` is that relation; Traeva saw this save, so usually `gap: false`. #33 and #34 use them as usual and need no changes.

**#31's model** (material section 6):

| Relation | Connects | Meaning |
|---|---|---|
| family member | `file_id` ↔ family | Which work it belongs to. A `file_id` belongs to at most one valid family at a time; merging families keeps the old identifiers and a merge record, and does not merge `file_id`s |
| Continue | parent snapshot → child snapshot | The child version continues the parent version |
| Branch | fork-point snapshot → the branch's first snapshot | Where a new branch starts |

- Version relations connect real snapshots, not file names. The child snapshot must exist; the parent snapshot may be empty, meaning unknown, and then no before/after comparison can be made.
- A child snapshot has at most one confirmed direct parent snapshot; a parent snapshot may have several branches. Nothing may point to itself, and no cycles may form.
- States (the JSON names are the planned names):

  | State | Meaning |
  |---|---|
  | `confirmed_system` | Confirmed, based on system evidence |
  | `confirmed_user` | Confirmed, based on the user's confirmation |
  | `candidate` | Candidate |
  | `unknown` | Unknown or not sure yet |
  | `rejected` | Judged unrelated by the user |
  | `disputed` | Disputed |
  | `superseded` | Corrected or replaced |

  The source of evidence and the user's decision are saved separately; a user confirmation is never upgraded to system evidence. There are three kinds of system evidence for `confirmed_system`: the file Memory was enabled for itself, the same physical object checked during relocation (v12), and since v45 the new object a replacement save leaves at the exact place of a record (the student's decision 10/14; `memory_auto_links` marks it as linked automatically, and the user can undo it).
- Only a relation whose state is `confirmed_system` or `confirmed_user`, that is not disputed, not replaced, and has both parent and child ends clearly known, can be treated as definite before/after versions.
- The floor does not change: the same hash, the same name or similar content does not merge `file_id`s and cannot by itself prove an association; with insufficient evidence, only a candidate or unknown is given.

### 4.3a Record chains, works and gaps (#31 M1a, implemented in v10, `family.rs`)

- A **record chain** is one record task: a series of watches joined one after another. Enabling Memory for a file without a record chain creates a new one, placed in this file's own work (family, member `confirmed_system`, basis `memory_on`). Enabling again for a file whose record chain has stopped **continues with the same record chain**: the quota is counted as before, candidate capture stays off, and the period it was off is recorded as a `memory_off` gap. Watches from before 0007 are backfilled by the migration: one work and one record chain per file, later watches recorded as reopenings, with `memory_off` gaps added; none of them enables candidate capture.
- Enabling Memory while the file is waiting for a decision in some record (a candidate, or exactly the unread object at an open record's place) returns `candidate_pending`; enabling the old file when the record chain has already continued onto another file returns `decision_conflict`.
- **Gaps** (`memory_gaps`): periods for which there is evidence that Memory may have missed saves; they do not mean the file changed. Each gap hangs after the record chain's latest version at the time it started; its start and its end are each written once, only in the round where the situation changes, not every 2 seconds.
  | Kind | Starts | Ends |
  |---|---|---|
  | `memory_off` | Enabled again after stopping (already ended when written) | When enabled again |
  | `capture_failed` | The recorded place cannot be captured (`problem` is the error code, for example `file_not_found`, `root_revoked`). A failure seen without the lock is looked at again inside the execution lock before writing, so that a move Organize is in the middle of is not taken as a failure | When the place is back to normal (`captured` / `recovered`); if the error code changes, or the place now holds an object Memory has not read, it ends with `changed` and a new one opens; on relocation (`relocated`) |
  | `replaced_uncaptured` | The recorded place holds another object Memory has not read (including a replacement found only during capture); since v45 only when the automatic link does not hold (§4.2b) | When back to normal, when the place becomes uncapturable again (`changed`), on an M1b decision, on an automatic link (`captured`, v45), or on relocation (`relocated`) |
  | `paused`, `lost` | The candidate quota pauses; the current object is judged unrelated | Quota released (`released`), switch turned off or record stopped (`stopped`), judged independent (`decided`); `lost` ends on stopping (`stopped`) or relocation (`relocated`) |
  
  `file_changing` (the file is still being saved) does not count as a gap. When a record stops, all unfinished gaps end with `stopped`. Every write rechecks inside a transaction that the watch is still the one open on the record chain and that the record chain has not lost track; otherwise nothing is written. When the storage itself is broken, a gap may fail to be written, and Traeva will not say it was recorded; after the storage recovers, if the failure is still going on, the next round writes the start.
- **Run periods** (`memory_runs`, the student's decision on #34, 2026-10-09): each time Traeva starts, it writes a run record before the first check or capture; after that it updates the "last running time" at least every 30 seconds and after each round that saved a new version. The time between the last time of the previous run and the start of the next run is a `watcher_stopped` gap, even if the content did not change after the restart (a change and a change back in between cannot be ruled out). After a crash this period is overcounted by at most 30 seconds; it can only over-report, never under-report. Runs are ordered by the order in which they were recorded; when the system time is set back between two runs, the span between the two times still counts as a gap (better to over-report). All times are the local wall clock; when the time is adjusted, a gap's position may be inaccurate. Closing only the window while the background still captures does not count as a gap. When the Mac sleeps the whole machine pauses, which does not count as a gap; seeing only the last state of several saves in a row between two rounds is a general limit and does not count as a gap either. Time before the first run record is `not_recorded` (only data from before 0007 runs into this).

- **The pending-confirmation page and decisions (v11, `family_decide.rs`)**:
  ```rust
  impl OrganizeService {
      pub fn candidate_capture(&self, chain_id: &str) -> Result<CandidateCaptureInfo, AppError>;
      pub fn set_candidate_capture(&self, request: &CandidateSwitchRequest) -> Result<CandidateCaptureInfo, AppError>;
      pub fn pending_candidates(&self, chain_id: &str) -> Result<PendingCandidatesView, AppError>;
      pub fn decide_pending_candidates(&self, request: &CandidateDecisionRequest) -> Result<CandidateDecisionOutcome, AppError>;
  }
  ```
  - The page lists all of this record's unprocessed candidates (in the order found; `seq` is unique and increasing but not consecutive); each item carries `continue_from`: the only parent version "continue" accepts, found by walking back from the record's latest version at the time the item was found, skipping objects judged independent, unknown or branch (`continue_skips` records how many were skipped; when it is greater than 0 the UI must present this relation as a new relation); when the walk meets an earlier object that is still waiting, it gives `continue_needs` (that object must be "continued" first in the same submission). The unread object at the place is also listed (`unread_occupant`).
  - `page_token` covers everything the page shows: the watch, the authorization, the switch, the lost state, the place, the latest version, the quota, every item and its snapshots, the object on site. If anything does not match at submission, `page_outdated` is returned (retryable) and nothing is written. Each page can be used only once.
  - Rules: the parent version of "continue" must equal the page's `continue_from`; excluding an intermediate item while skipping over it in the same batch returns `decision_conflict`: the judgment on the intermediate item must be submitted on its own first, and after a refresh, the user confirms the new relation the page shows; a branch's parent version must be in `fork_points` (on the line, or in a branch whose starting point is known) and must have been saved before this object; "not sure yet" only records a decision and does not release quota, but it does change the page (the token includes each item's count of "not sure yet").
  - How it is written: continue → relation `continuation` (`confirmed_user`, with the skip count); branch → `branch` (`confirmed_user` with a parent, `unknown` if the parent is unknown); unknown → `unplaced` (`unknown`), with the members all changed to `confirmed_user`; independent → member `rejected`, no relation created.
  - An object at the place that is not a waiting candidate (`current_object`) has only two options (material sections 2 and 3: when candidate capture is off, the new object's body is not read for the pending-confirmation page, and confirming only its ownership does not save the body either). Since v45 a new object at the place is first linked automatically by §4.2b, and once linked it does not appear here; only those that cannot be linked (or were left from before v45) are the unread objects here:
    - "Continue": the user authorizes reading it and continuing to record from it. What is read must be the object the page showed, and the record at the place must still be the one from the look; otherwise `page_outdated`. After the read it is registered as a candidate (reason `read_on_decision`, state continued), and the uncaptured period is recorded as `replaced_uncaptured` (already ended when written).
    - "Independent": not read. It can be chosen when the place holds an unread object, an already decided file, or another record's file.
    - To say it is a branch or of unknown order, first turn on candidate capture (D2 will save it), or enable Memory for it separately.
  - The object at the place judged independent: the switch is turned off (`occupant_independent`), the record loses track (an unfinished `lost` gap), and nothing is looked at afterwards. An earlier object judged independent rejects only that one item.
  - Continuing the object at the place: in the same transaction, stop the old watch (not revived) and open a new watch on the new object (same record chain, link `continued` carrying that decision); the switch and the quota go with the record chain. When "continue" is confirmed but the watch did not move, `history_only` is true: the record has stopped, the authorization was revoked or the record lost track, or what was continued was only an earlier object not at the place. After that, enabling Memory for the latest file on the line continues with the same record chain; enabling a file that is not the latest returns `decision_conflict`.
  - Before reading any object (candidate capture, D2, deciding "continue" for the current object), if there is an unresolved Organize operation in the same authorized folder, it does not read and returns `unresolved_action`.
  - When the same physical object already has a record elsewhere (for example another Memory file `mv`'d to this place), it is handled as "another record's file": only reported, not read.
- **Manual relocation (v12, `relocate.rs`, material section 4 and its supplement)**:
  ```rust
  impl OrganizeService {
      pub fn relocation_preview(&self, chain_id: &str, root_id: &str, picked: &Path) -> Result<RelocationPreview, AppError>; // look only; no reading, no writing
      pub fn relocate_record(&self, request: &RelocationRequest) -> Result<RelocationOutcome, AppError>;
  }
  ```
  - The user picks the file's current place with the picker; the system does not search the whole disk and does not follow temporary files. Only an open record (including a lost one) can be relocated; a stopped record returns `record_stopped`: Memory was not recording it at that time, so Memory can be enabled separately for the file at the new place and then joined back to the work with M2b's merge. What is looked for is the latest file on this record line: usually the watch's file; if an earlier candidate was confirmed "continue" while the watch did not move (only history confirmed), it is that candidate, found by following the confirmed continue relations forward. After the line has already continued elsewhere, picking the object of the watch's file returns `decision_conflict`: continuing again would give the work two ends.
  - The picked file must: be in a currently valid authorized folder (the path the picker gives is first resolved to its real place the way Organize resolves a picked file; a path not in an authorized folder returns `outside_root`; after that it is opened level by level from the authorized folder's handle, not following symbolic links); be the same physical object as the recorded file (same device number, inode and creation time); and have only one link. Otherwise `not_same_object` is returned (a copy, a file on the volume of another authorized folder, a hard link, another file, a folder, or the symbolic link itself), nothing is written, and the record keeps waiting. When the path itself cannot be used, the observation's error code is returned: a hidden name, or a mount point inside the authorized folder (another volume), is `unsupported_file`; an app bundle or project folder is `protected_location`. The read at confirmation must be stable (unstable returns `file_changing`), and what is read must still be that object (swapped returns `page_outdated`). These physical fields are only evidence for the check; they do not merge two `file_id`s.
  - The original place is looked at once more too; if it cannot be looked at (for example the original folder's authorization was revoked), that error is returned and there is no relocation. If it still holds the recorded file, `decision_conflict` is returned (no relocation needed); the only exception is a lost record: the file came back to the original place, the user picks the original place, the preview's `old_place_holds` is `recorded_file`, and after confirmation the `lost` gap ends (`relocated`), the original watch continues recording, no new watch is opened, and if the content changed a new version is saved. The object now at the original place (empty, an unread object, a candidate, another record's file) does not join the work because of the relocation. Candidates saved there are kept and decided on the pending-confirmation page as usual; but the version they were found at has already continued at the new place, so "continue" is no longer offered (`continue_from` is null, and the same for the candidates after it); only branch, unknown order, independent or not sure yet can be chosen. Judging it independent does not make the record lose track either.
  - The picked file already has its own Memory record, or is already in a work: returns `decision_conflict` (this belongs to M2b's merge).
  - `RelocationPreview`: `chain_id`, `old_place`, `old_place_holds` (`empty` / `unread_object` / `pending_candidate` / `decided_candidate` / `other_record`; for a lost record whose file came back to the original place it is `recorded_file`, and then `new_place` is the original place in the record, even if the name the picker gave differs in case), `new_place` (`root_id`, `relative_path`, `display_path`), `byte_length`, `modified_at_ms`, `waiting_candidates`, `candidate_capture`, `page_token`. The confirmation request `RelocationRequest`: `chain_id`, `root_id`, `relative_path` (exactly the same as `new_place`, and only a plain relative path), and `page_token`; extra fields are refused. The token covers everything the preview shows: the record, the watch, the latest version, the original place and which object is there (only which one, not its content), the physical evidence, size and modified time of the file at the new place, the switch, the waiting count. `waiting_candidates` is the number of all unprocessed candidates of this record. Submitting the same confirmation a second time returns `decision_conflict` (the file is already at the recorded place). If anything changes after the preview (for example the file is edited again), `page_outdated` is returned, and nothing is read or written.
  - On confirmation, everything above is looked at again inside the execution lock; if any authorized folder has an unresolved Organize operation, `unresolved_action` is returned. Then the file at the new place is read once, and in the same transaction:
    - Register it by Organize's rules (§4.1: usually a new `file_id`; if that path already has a registration Organize made for the same object with no Memory record yet, that one is reused), save its snapshot, and record a decision (`relocate`);
    - The old file record is marked `missing`: its object was just found at the new place and has only one name, so it is no longer at the old path (the same way Organize records its own moves). If the file is later moved back to a place used before, it gets yet another new file record and can be relocated just the same;
    - Stop the old watch (not revived) and open a new watch on the new file: same record chain, link `relocated`;
    - The new file becomes a work member (`confirmed_system`, basis `relocation`), and a continue relation (`confirmed_system`) is recorded from the old file's last version to the new file's first version;
    - Gaps at the original place (`capture_failed`, `replaced_uncaptured`, `lost`) end with `relocated`. The move itself was not seen: if there is no gap yet that starts from the old file's last version, one is added (already ended when written), so a snapshot pair across the move always carries a gap;
    - The quota and `paused` are unchanged. When candidate capture is on, it moves with the record chain to the new place and looks only at the new place.
  - Result `RelocationOutcome`: `record` (the record at the new place) and `snapshot` (the first version of the new file record; when a lost record comes back to the original place, it is that file's latest version, which is a new version only if the content changed). The problem left by the old watch's last look (file not found, lost) is cleared along with it.
- **Merging works and the same-hash hint (v14, `works.rs`, `family_merge.rs`, migration 0008; material section 2 third kind of source, section 6, the student's decision in #31 on 2026-10-10)**:
  ```rust
  impl OrganizeService {
      pub fn memory_works(&self) -> Result<Vec<WorkSummaryView>, AppError>;            // current works, oldest to newest
      pub fn merge_preview(&self, family_id: &str, other_family_id: &str) -> Result<MergePreview, AppError>; // look only; no writing
  ```

  - A merge never rewrites existing rows: the merged-away work's members, relations and record chains all keep their original IDs, and from then on that ID stands for the work it was merged into (view `memory_live_families`).   - Preview: the two works (`stays`, `joins`, both `MemoryFamilyView`), and the old "unrelated" judgments the merge would override (`overrides`: files judged unrelated on one side that are confirmed members or candidates on the other side).   - **Same-hash hint**: when Memory is enabled for a file that belongs to no work (the record chain starts with `started`, and the basis of the file's earliest member row is `memory_on`), the SHA-256 of its first version is compared with the versions of other works' confirmed members saved **before it**. A match is only a hint, put in `same_content` (`family_id`, `own_version`, `same_bytes_as`, one per work, at most 10), and never becomes a relation, candidate or snapshot pair (material section 7: the same hash only shows that the content is the same). Empty content (0 bytes) gives no hint; nor is there a hint when the two sides are already the same work, or when this file was judged unrelated in that work. The hint is computed on every read and not saved.
  - 0008 also built the tables and rules M2b-2/M2b-3 need: the work-level decision kinds for associating, correcting and moving out; change records; paused records (`memory_record_holds`; while paused, no new watch can be linked to the record chain); changing a relation to disputed or replaced, or a member to replaced, must have a change record first (marking a member disputed directly is still allowed; #33/#34's tests do this). None of these are used yet in v14.
  - Fix: a file whose line has already continued elsewhere (its last version already has a continue relation) cannot have Memory enabled again; this returns `decision_conflict`.
- **Associating with a work (v15, `family_associate.rs`; material section 2 fourth kind of source and its supplement, section 5, section 6, section 7 "Save As")**:
  ```rust
  impl OrganizeService {
      pub fn association_preview(&self, family_id: &str, root_id: &str, picked: &Path) -> Result<AssociationPreview, AppError>; // reads once to compute the hash only when there are no versions; no writing
      pub fn association_preview_for_file(&self, family_id: &str, file_id: &str) -> Result<AssociationPreview, AppError>; // no reading, no writing
      pub fn associate_file(&self, request: &AssociationRequest) -> Result<WorkDecisionOutcome, AppError>;

  ```
  - The user picks a file (chosen with the picker, or a file Traeva already knows, such as the one the same-hash hint mentioned) and a work, and states their relation. The page shows the file, the work and the known evidence (`same_bytes_as`: versions among the work's members with exactly the same bytes, empty content not counted; `same_object_as`: member files that are the same physical object). Evidence is only shown and never becomes a relation by itself (material section 7).
  - The file's standing (`standing`) decides what can be chosen:

    | standing | Meaning | Choices |
    |---|---|---|
    | `not_recorded` | No saved versions, not in any work | `unknown` (only confirms ownership and creates no relation: a relation needs real versions), `independent`; `needs_recording: true`: after Memory is enabled, associate once more to fix its position |
    | `saved_no_work` | Has versions, not in any work (for example a candidate judged unrelated elsewhere) | `continue`, `branch`, `unknown`, `independent` |
    | `in_other_work` | A member of another work | `continue`, `branch` and `unknown` all merge that **whole work** in (`merge_scope`; a file belongs to only one work at a time); `independent` only records an unrelated judgment here and leaves that work untouched |
    | `member_without_parent` | A member of this work whose first version has no known parent version (for example after a merge) | `continue`, `branch` (to give it a position) |

    When the file has already been judged unrelated in this work, `independent` is no longer offered; choosing a positive option overrides that judgment (listed in `overrides`, changed to `superseded`).
  - `continue`: continue from the **last** version of some member of the work, on a line that has not yet continued elsewhere (`continue_from`). A record (open or lost) whose line ends with this version stops along with it (`stops_record`; material section 5 "the old watch stops"). **No new watch is opened and no watch is moved**: if the file has its own record it records as usual; if not, Memory must be enabled separately (material section 2: associating is not enabling Memory). `branch`: branch off from any version of a member saved before this file's first version (`fork_points`). Both are `confirmed_user`; Memory saw nothing between the two versions, so this snapshot pair is always `gap: true`, with `skipped`. An existing "order unknown" relation on the file's first version (`replaces_unknown_placement`) is first changed to `superseded`.
  - Reading: only a file chosen with the picker that has no versions yet is read, once and stably, to compute SHA-256, inside the execution lock and only when the authorized folder has no unresolved Organize operation; the body is not saved, no snapshot is created, no watch is opened (material section 2 supplement). A file with versions is never read: the relation's endpoint is its first saved version. On confirmation it is read again, and if the object or the hash changed, `page_outdated`; then the file is registered by Organize's rules (registered only; no version saved).
  - Writing (one transaction): one work-level decision (kind `associate`, with `file_id`, `choice`, `parent_snapshot_id`, `evidence`: `same_bytes` / `same_object` / `none`, and with `other_family_id` and a merge record when merging); every new member and relation and every changed state has a change record first (`memory_work_changes`). `not_recorded` / `saved_no_work`: member `confirmed_user` (`rejected` for `independent`), basis `user_decision`; `saved_no_work` choosing `unknown` also adds an `unplaced` relation. `in_other_work` choosing `unknown` only merges.
  - The token covers: the file (ID, place, physical object, hash), its first version, its standing, the choices, each parent version and the record it would stop, the fork points, the evidence, the overridden judgments, and both works' `work_token_lines`. If a work member saves a new version (the continuable parent version changes) or a record changes, the page becomes outdated; this file saving again does not. Each page can be confirmed only once.
  - `AssociationPreview`: `family_id`, `subject` (`file_id`: null for a file chosen with the picker that is not yet registered; `place`; `sha256`; `versions`), `request_subject` (passed back as is on confirmation), `standing`, `other_family_id`, `merge_scope`, `needs_recording`, `evidence`, `choices`, `continue_from` (`parent`, `stops_record`), `fork_points`, `replaces_unknown_placement`, `overrides`, `page_token`. `AssociationRequest`: `family_id`, `subject` (`{"kind":"picked","root_id","relative_path"}` or `{"kind":"file","file_id"}`), `choice` (`{"kind":"continue"|"branch","parent_snapshot_id"}`, `{"kind":"unknown"}`, `{"kind":"independent"}`), `page_token`; all of them refuse extra fields.

- **Correcting a relation (v17, `family_correct.rs`; material section 7 "error correction", the state table of section 6, the last paragraph of section 8, the student's decisions 1 and 4 of 2026-10-10)**:

  - **Undo** (`revoke`): the relation is changed to `superseded`; the child version goes back to "same work, order unknown" (a new `unplaced` / `unknown` relation is written, the same way as in M1b); membership does not change (material section 7: family ownership does not change automatically). It is not relinked by itself: the only way to create a relation again is "associate with a work". The `memory_auto_links` row is kept.

Disputed relations come only from moving out members (M2b-3b).
  - **Record line segments**: a record line (the files the record looked at, and the files confirmed as continuations) is joined into one segment by confirmed continues. When one of those continues is undone, the line breaks there and the later part becomes a separate segment:
    - Its sending permission is that of this segment's first file (`permission_file_id`, the snapshot pairs' `permission_file_ids`);
    - Its position in the work is unknown (snapshot pairs have `unplaced: true`), unless another confirmed relation links it;
    - `usable_pairs_of_line` and `line_versions` count only the segment the file is in.

    A line that never had an undo is one whole segment, the same as before.
  - **Paused records**: for the file a record is watching, if after the undo the first file of its segment changes (the record's automatic recording was based on exactly this undone continuation, material section 7 last item), then in the same transaction: the watch stops, candidate capture is turned off (`corrected`), unfinished gaps end (`corrected`), and a pause is written (`memory_record_holds`). `MemoryRecordView.hold`: `work_decision_id`, `edge_id`, `held_at_ms`, `why` (`relation_revoked`); `state` is `stopped`.
    - The user enables Memory again for the record's file (`start_memory_for_file`): the same record continues, the pause is lifted (`resumed`), a `memory_off` gap is recorded for the time in between, candidate capture stays off, and the quota is kept; from then on this segment uses its first file's sending permission.
    - Stopping the record (`stop_memory_record`): the pause is lifted (`stopped`).
    - Undoing a branch, or undoing a continue the record is not on, pauses no record.
  - Preview: `family_id`, `relation` (`VersionRelationView`; v45 adds `linked_automatically`: this relation was linked automatically by Traeva, also present in the work view's `relations`; it says who made the link, and stays true after a later undo or confirm again), `can_revoke`, `can_confirm_again`, `leaves_unplaced` (the version whose order becomes unknown after the undo), `records_held` (the records that would pause), `page_token`. `RelationRequest`: `edge_id`, `action` (`revoke` / `confirm_again`), `page_token`; extra fields are refused. The token covers this relation (ID, state, both ends), the records that would pause and their watches, and the work's `work_token_lines`. Each page can be confirmed only once. `WorkDecisionOutcome` adds `held_records` (the records paused this time).
  - An old pending-confirmation page or relocation page carries the old watch's token; submitting it after the pause returns `page_outdated`, and after a refresh it is `record_stopped`.
- **Moving out members (v19, `family_move.rs`; material section 7 "error correction": when family ownership is also wrong, the user explicitly chooses the members to move out; the student's decisions 2 and 3 of 2026-10-10)**:

### 4.4 Text extraction (`TextExtraction` / `TextSummary`)

`read_text(file_name, bytes)` picks a reader by extension and is a pure function of (file name, bytes, reader version); the same snapshot always gives the same text.

| Field | Meaning |
|---|---|
| `reader` | The reader and its rule version, such as `txt-md-1`; `none` when there is no reader |
| `status` | See the invariants below |
| `chars` | The number of Unicode scalar values in `text` |
| `covered` | What was read, described in the reader's own words |
| `left_out` | Content that **actually exists** in these bytes but was not read; it does not list things the reader generally does not handle that are also absent from this file |
| `note` | The reason for a status other than `complete`, for people to read, with no file content |

Invariants all readers follow (checked by tests for TXT/MD):

| `status` | Text | `covered` | `left_out` | `note` |
|---|---|---|---|---|
| `complete` | Present (may be empty or whitespace only) | Non-empty | Empty | None |
| `partial` | Present | Non-empty | **Non-empty** | Present |
| `unsupported`: a type, encoding or feature not handled (encryption, etc.), or over the reader's resource limits (number of archive entries, decompressed size) | Empty, `chars` = 0 | Empty | Empty | Present |
| `failed`: should be readable, but the bytes are damaged (invalid UTF-8, a damaged archive) | Empty, `chars` = 0 | Empty | Empty | Present |

- `text` uses only `\n` for line breaks; it exists only in core's memory, its type is not serializable, and it never goes into IPC, the database or logs; its `Debug` output shows only the length. `TextSummary` contains no body text and may be shown and saved.
- This restriction applies to the `TextExtraction` type itself. To show the basis of changes in the local window, B may carry excerpts **with a length limit** in its own DTOs; the limit and whether they are saved are decided by B in #33/#35 according to the privacy requirements; excerpts are not written to logs and do not go into Organize's tables.
- The limit `MAX_MEMORY_TEXT_CHARS = 1_000_000` **applies to all readers**: text read beyond the limit is truncated, the result is always `partial`, and `left_out` states the remaining part.
- TXT/MD (`.txt`, `.md`, `.markdown`) use the same decoding function as Organize, `observe::decode_text`: strict UTF-8, BOM removed, CRLF/CR → LF; UTF-16 and NUL are `unsupported`, invalid UTF-8 is `failed`.
- **DOCX (`.docx`, connected in v21, reader `docx-2`, `docx.rs`, #66 Codex-D)**: `read_text` dispatches to `read_docx(bytes)` by the case-insensitive `.docx` extension (there must be a name before the dot). It reads only the bytes in memory: it does not open paths, does not use the network, does not unpack ZIP entries to disk, does not access external relationships, and does not execute content.
  - It reads the Word body text: each paragraph becomes one line, and it reads the text of runs, tabs, explicit line breaks and empty paragraphs. The exact coverage, refusal cases and limits are in [docx-reader.md](../features/docx-reader.md).
  - The invariants in the table above apply too: what is read goes into `covered`; what is in this file but not read (tables, headers and footers, footnotes, comments, fields, etc.) goes into `left_out` with status `partial`, and must not be silently dropped. Encryption, macros, features not handled and resource limits are `unsupported`; damage is `failed`; `note` uses only fixed explanations and contains no file content.
  - The same bytes always give the same result, and `reader` is always `docx-2`, so B's rule of re-comparing by reader version is unchanged. Whenever the reader's behavior changes, the version number is incremented.
  - **The cached text of citation fields does not go in here**: `docx-2` does not read it. D's `read_docx_cached` (`docx-cache-local-1`) is used only for §4.7's local preview, never for comparison, retrieval or sending to the model (the student's decision 10/11).
  - **Flattened citations are still body text** (v22, D103-02, R126-02): `docx-2` can only recognize citations that still keep their field structure (the field code and its cached text), and leaves those out. If a citation has already become plain text, for example its field was unlinked in Word, or the reference manager converted it to plain text, then it is part of the body: `docx-2` reads it, and sends it when there is sending permission. The reader cannot tell where this text originally came from. So the permission notice and the UI may only say "citations in fields are not read or sent", and must not say "text generated by the reference manager is never sent".
  - Organize does not read .docx (it is not a text type; `observe::is_text_file_name` is unchanged); old Word versions still cannot be opened in Word (§4.7).
  - The student's decisions:
    1. 2026-10-10 ([#100 issuecomment-6101881983](https://github.com/P30g53/Traeva/pull/100#issuecomment-6101881983)): content without readable body text (for example a whole document that is only one table) is `unsupported`, with `note` stating what was omitted; the 200:1 compression ratio limit is kept.
    2. 2026-10-11 ([#66 limited Go](https://github.com/P30g53/Traeva/issues/66)): approves DOCX body text reading, snapshots, semantic changes and retrieval, and a local plain-text preview of historical DOCX. Connecting DOCX changed what Memory will send, so B raised `MEMORY_NOTICE_VERSION` to 2 (#124); **all files already agreed to (including TXT/MD) must be agreed to again under the version 2 notice** before anything is sent. #103 must not take effect before #124.
- **PPTX and XLSX (v23, the student approved connecting them fully to Memory on 10/12; v24: connected. `read_text` dispatches `.pptx` / `.xlsx` to `read_pptx_memory` / `read_xlsx_memory`, and the preview uses `read_pptx_preview` / `read_xlsx_preview`; the experimental entry points and the typed `Workbook` interface in E's and F's modules, meant for the verification crates, are not called in core)**: the PPTX reader is written by E and the XLSX reader by F; the wiring and this section's shared functions are A's responsibility; comparison, analysis, retrieval, UI and the permission notice are B's.
  - **Two projections**, both `TextExtraction`, no new DTO:
    - **Memory projection** (`read_text` dispatches by the case-insensitive `.pptx` / `.xlsx` extension, with a name before the dot; readers `pptx-1`, `xlsx-1`): used for comparison, analysis, retrieval and sending to the model. It contains only **visible** content: the titles, body text and speaker notes of PPT's visible slides; the text, numbers, formula source and cached values of Excel's visible sheets. Hidden slides (slide part `<p:sld show="0">`) together with their notes, and hidden / veryHidden sheets (the `state` in `workbook.xml`), are not included; this is stated in `left_out`, for example `hidden slides (2), not included in Memory`, and the status becomes `partial` accordingly. Filtering is done by the reader from the package structure, never guessed from flattened text.
    - **Preview projection** (readers `pptx-preview-1`, `xlsx-preview-1`): used only for §4.7's local historical preview; it includes hidden content and marks it hidden with structure lines. It does not enter comparison, analysis, retrieval or sending.
    - **Truncation and line breaks** (E's question): when cutting to `MAX_MEMORY_TEXT_CHARS`, a generated structure line is never split, nor is an escape `\` at the start of a source line split from the first character after it, so the text kept may be slightly less than the limit; `left_out` truthfully states the full projection minus the number of characters actually kept. Slide segments and sheet segments are joined with a single line break only, with no extra empty lines; the source's own empty lines are kept.
    - **When only structure lines remain** (F's question 3): if the projection has only generated structure lines and not a single source line (for example all slides or sheets are hidden, or the visible part has no stored text), the status is `unsupported`: `chars` is 0, `covered` and `left_out` are empty, `text` is empty, and `note` uses a fixed explanation, for example `No visible stored text: Memory includes visible slides or sheets only.`. Structure lines must not inflate the result into `partial`. The preview projection shows hidden content as usual.
  - **Structure lines**: structural descriptions the reader generates, each on its own line.
    - **Valid only for the four readers above**. The output of TXT/MD, `docx-2` and other readers is not escaped and has no structure lines: a `⟦…⟧` line the user wrote is source text.
    - A structure line starts with `⟦` (U+27E6) and ends with `⟧` (U+27E7), and the fields in between are separated by ` · ` (U+00B7, with one space on each side). Recognition checks the whole line as is, without trimming spaces.
    - **Source escaping**: in these four readers' output, a source line that starts with `⟦` or `\` gets a `\` in front. So a line that starts with `⟦` is always a structure line. The UI removes this one `\` when showing source text; positions such as `QuoteAt.char_start` are still computed on the reader's output.
    - **Source text inside structure lines** (currently only sheet names) is written as a JSON string, with `"`, `\`, control characters, `⟦`, `⟧` and `·` all written as `\uXXXX`. That way neither splitting fields on ` · ` nor finding the closing `⟧` can be disturbed by the name.
    - PPT: `⟦slide 3 · id 257⟧` (3 is this slide's ordinal in the presentation, hidden slides counted, so after hidden slides are filtered out the slide numbers in the Memory projection may have gaps, matching the numbers seen in the preview and in PowerPoint (E's question); `id` is the `sldId` in `presentation.xml`, used to detect reordering), `⟦title⟧`, `⟦text⟧`, `⟦notes⟧`; a hidden slide in the preview projection is written `⟦slide 4 · id 260 · hidden⟧`. Notes must be under `⟦notes⟧` and never mixed with the body.
    - Excel: `⟦sheet 1 · id 1 · name "F Data"⟧` (1 is the declaration ordinal, hidden sheets counted, so there may be gaps after filtering; `id` is `sheetId`); a hidden sheet in the preview gets `· hidden` or `· very hidden` at the end. Each field of each non-empty cell has its own label line, followed by the source line: `⟦cell C2 · literal · number⟧`, `⟦cell C2 · formula⟧`, `⟦cell C2 · cache · number · not verified⟧`. The value types are `number` / `text` / `boolean` / `error` / `date`; the formula is written as the source in the package, without adding `=`; the cache always carries `not verified`.
      - **Empty values and no cache** (F's question 2): a cell with no value (only a style, or an empty `<v/>`) gets no `literal` line. If a formula's cached value is empty, write `⟦cell C2 · cache · blank · not verified⟧`, with no source line below it; if the formula has no cached value in the package at all, write `⟦cell C2 · cache · missing · not verified⟧`, also with no source line below it. Text that is an empty string is written as `text`, followed by one empty line. These lines are all generated status descriptions, not source evidence; "no cache" must never be written as a made-up value.
      - **No `part`** (F's question 1): the sheet's part path in the package (such as `xl/worksheets/sheet1.xml`) stays only in the reader's internal `Workbook` and does not go into the projection. What the user can see stops at the sheet's ordinal, `id`, name, cell address and field. Line breaks in cell text are split into several lines as they are. Cells are ordered by the sheets' declaration order, then by row and column. Shared formulas that have no text in the package are not expanded into made-up formulas; they are written in `left_out`.
  - **Shared recognition function** (A, `reader.rs`): `structure_line(reader, line) -> Option<StructureLine>`. When `reader` is not one of the four above, it always returns `None`. B's comparison, basis check, retrieval and evidence locating all use only this function, and do not write their own regexes. A also provides a TS mirror for the preview UI.
  - **Generated structure lines are only structural context, not source evidence**: #125's basis check looks only at source lines, and quotes can be taken only from source lines. The evidence's place (slide, role, sheet, cell, field) is taken from the nearest structure line above the change, found by B from the full text in `change_lines`.
  - **Comparison rules** (B, `changes.rs`). The structure-aware rules below **take effect only for readers that output structure lines**, so **`DIFFER_VERSION` is not raised**: raising it would re-compare and re-analyze all existing TXT/MD/DOCX version pairs, and after agreeing again the old content would be sent again in bulk. New readers have new names anyway and never touch old version pairs.
    - Parts where only structure lines changed (for example a slide added in front, so all later slide numbers change): not sent to the model.
    - PPT slide segments that correspond one to one by `id`, with every segment's content the same and only the order different: recorded as a slide order change and not sent to the model (a new state of B's `PairState`). If an `id` is missing or duplicated, or the correspondence is incomplete: compare by lines as usual, and state that it cannot be confirmed whether this is only a reordering. Splitting slides, merging slides and permanent slide identity are out of scope for this version. Sheet order changes are handled by `id` in the same way.
      - **The definition of a segment and of "same content"**: a slide segment starts at `⟦slide N · id X⟧` and ends before the next slide label (the notes are in the segment). Slide segments on the two sides are matched by `id`; the comparison ignores the ordinal N in the slide label, and all other lines must be identical. Sheet segments likewise run from `⟦sheet N · id X · name …⟧` to before the next sheet label, ignoring the ordinal N; if the sheet name changed, it does not count as "only the order changed".
    - **How structure-only changes are stored** (B, #152): stored as `memory_pairs.outcome = 'no_text_change'` (`hunks` 0), with `note` holding one structure code: `structure:slide_order` (slide order change), `structure:sheet_order` (sheet order change), `structure:sheet_renamed` (only a sheet name changed), `structure:labels` (only structure lines changed). B then maps them to `PairState`'s `StructureOnly`. No new migration: 0004 has no constraint on `note`, and the CHECK on `outcome` is unchanged. None of these are sent to the model; a sheet rename was made by the author, so the UI must say "renamed the sheet", never "only labels changed".
    - Excel is compared by sheet and cell address, without aligning logical rows and columns; after rows or columns are inserted or moved, there is no guarantee of matching the same record.
    - **Quotes for short lines** (v24, found by B testing with F's real Excel files): the numbers in cells often have only 1–2 characters (5 → 7), not enough for a 3-character quote. Such a line may be quoted whole: the quote must be exactly one whole line on this side, and the other side must have no identical line. A quote must still have at least one letter or digit.
    - **The "not fully read" flags in the request** (v24): `earlier_version_partly_read` / `later_version_partly_read` (formerly `…_cut_short`) sent to the model mean this version's reader did not read everything: it may be truncation, or parts left out by design (hidden slides, sheet formatting, etc.), not only truncation. Real Excel files always have formatting, so almost every pair is partly read, and the UI shows "Described in part" accordingly.
    - Hidden slides or sheets are not in the projection: a whole slide or sheet disappearing may only mean it was hidden. The prompt requires saying "no longer included", never "deleted".
    - **Snippets sent to the model** (v25, #166, R1-M28-O1; v28, #171, R1-M28-O4):
      - Every PPT/Excel snippet carries `place`, saying where the changed lines start: for PPT `{ slide, part }`, for Excel `{ sheet, cell, field }`, computed from structure lines by B's `place_line` / `place_of`. Since v28 Excel's `sheet` is the sheet's ordinal (the N in the structure line); when a whole sheet is hidden or added, or the change starts at the sheet label, the place is only `{ sheet }`. The `HunkPlace` DTO is unchanged (the sheet name the page shows is still in it); the ordinal is added only in the JSON sent to the model.
      - **Sheet names are not sent**: they are text the author wrote, may be far from the change, and sending them would widen what is sent. v25 only removed the sheet name from `place`; when a sheet structure line fell in `removed`, `added` or the context, the sheet name was still sent (R1 caught this offline with an example that hid a whole sheet; nothing was actually sent). Since v28 the sheet structure lines in all four line groups (`context_before`, `removed`, `added`, `context_after`) are rewritten to `⟦sheet N · id X⟧` before sending. The rewritten line still starts with `⟦` and is still treated as a structure line: it cannot be quoted, and quotes and the basis check work as before. Pages and previews reread the snapshot and show the sheet name as usual.
      - A sheet name that appears in a cell's text or formula (for example a formula that references another sheet) is that cell's own content; it is sent like any other changed line and is not rewritten.
      - Old analysis descriptions already saved (from when the model could see sheet names, under `memory-changes-3` / `-4`) that contain sheet names are sent as saved descriptions during retrieval. That data was already sent at the time and is within the scope of Memory notice v4, so it is not rewritten or reanalyzed.
      - The context above an Excel change starts from the first structure line (a cell label); source lines before the label are not sent. Reason: in row order, a neighboring column's heading sits right above the change, but its label is not in the context, so the model would mistake it for the name of the changed cell. The context below the change is unchanged.
      - The prompt requires calling a changed cell by its address (for example "cell A2 changed from 5 to 7"), and never using another cell's text as its name or meaning. Since v28 the prompt's structure line example is `⟦sheet 1 · id 1⟧`, and the prompt explains that sheet names are not sent and that sheets are called by ordinal (for example "sheet 2"). `CHANGES_PROMPT_VERSION` = `memory-changes-5` (`-4` in v25); old analyses are kept.
      - The options of clarification questions must keep the qualifier "no longer included / may have been hidden", never "removed" or "deleted" (R1-M28-O2); `QUESTION_PROMPT_VERSION` = `memory-question-2`.
      - What is sent only shrinks, never grows: `place` is a position the reader generates, not body text. So the permission notice is unchanged and no new agreement is needed.
      - Trade-off: Excel descriptions are mainly by cell address, so retrieving by heading text (for example "station count") may find nothing.
    - Only `cache` lines changed: must not be described as "changed the formula" or "recalculated". `CHANGES_PROMPT_VERSION` is incremented (it is saved only with the analysis row and does not trigger reanalysis); the retrieval prompt is incremented as needed.
  - **Unchanged**:
    - Input goes only through `read_snapshot`, the hash is checked every time, and a missing or damaged snapshot fails directly, with no fallback to the current file;
    - Derived results are bound to the snapshot ID and the reader version;
    - The quality status and actual omissions are passed all the way to the UI;
    - Resource limits are not relaxed (for PPTX see `docs/features/pptx-reader-experiment.md`, for XLSX see `experiments/xlsx-reader/RESEARCH.md`);
    - No image recognition, OCR, full layout, formula recalculation, macros or external links.
    - XLSX status mapping: `complete_within_profile` → `complete`; actual omissions → `partial`; `failed` → `failed`; `unsupported` / `resource_limit` → `unsupported`, with the specific refusal code written in `note`.
  - **Permission**: connecting PPTX/XLSX changed what Memory will send. B raised `MEMORY_NOTICE_VERSION` to 4, with the notice stating that PPT includes notes, Excel includes formula source and cached values, and hidden content is not sent; all files already agreed to must be agreed to again, with a regression run of TXT/MD/DOCX. The reader wiring (`read_text` dispatch) must not take effect before the version 4 notice does, the same approach as #103 / #124.
- Results derived from text (B's changes, evidence line numbers, etc.) save `snapshot_id`, the `reader` version and the range; when the source text is needed, the snapshot is reread. Whether to save short excerpts separately is decided by B according to #33's privacy requirements.

### 4.5 Source association evidence (C, #27)

### 4.7 Old-version copies (B, #35, v8)

When an old version is opened, the user sees a **new read-only copy**, not the user's file and not the snapshot itself. So no app can change a snapshot.

- **Location**: `opened/<random UUID>/<name>` under app-data. `opened` is in `TRAEVA_NAMES` in `app_data.rs`, so a test app-data directory with copies in it is still accepted at the next startup. Nothing is written inside an authorized root.
- **How it is written**:
  1. The bytes are taken only from `read_snapshot` (SHA-256 checked); `snapshots/` is never opened directly.
  2. Directories are opened level by level with fds from app-data, not following symbolic links, with permissions 0700. It reuses `open_app_data` / `open_child` (`pub(crate)`) from `snapshot.rs`. The random UUID directory is created with `mkdirat`; on `EEXIST` another one is picked.
  3. The file is created with `O_CREAT | O_EXCL | O_NOFOLLOW` and never overwrites. After writing: F_FULLFSYNC, read back and check the SHA-256, then change to 0444. If the write is incomplete, this file is deleted.
- **Name and whether it can be opened**: only text files Memory can read (`observe::is_text_file_name`: .txt, .md, .markdown, case-insensitive) keep the extension, with `can_open: true`, and the name is "name (version N).extension".
  - N is this version's number on the record line, consistent with the history page and retrieval results: counted in the saved order of `usable_pairs_of_line`, and 1 when the file has only one version (v20, #131). The file's own `sequence` is not used: editors that save by replacement start counting from 1 every time (R2-MEM-10). A version not listed on the record line has no number, and its name is "name (an older version).extension"; the two fallback names below become `older-version.extension` and `older-version` accordingly.
  - For hidden files (starting with `.`), names containing `/` or `\0`, or names over 200 bytes, the name becomes `version-N.extension`, still with `can_open: true`.
  - Every other type is called `version-N`, without an extension, with `can_open: false`. Reason: `/usr/bin/open` picks the app by extension, for example `.terminal` is handed to Terminal to run and `.dmg` gets mounted; and the copy is a file Traeva newly wrote, without the quarantine mark the original file might carry, so the system's check on first opening would be skipped. This still holds after v21 connected DOCX: a .docx is `version-N`, `can_open: false`. The student's decision 10/11: opening old Word versions in Word remains No-Go; the UI uses the local preview below instead.
- **Opening**: opened only when the user clicks and `can_open` is true. `memory_commands.rs` calls `/usr/bin/open` with only one argument: the copy's absolute path. It returns `OpenedVersion { copy, opened }`; `opened: false` means opening is not allowed or macOS failed to open it; the copy is still in place, and the UI shows its location. The UI must state "this is a read-only copy, not the original file".
- **Write failure**: delete the half-written file and its UUID directory.
- **Retention**: not cleaned up in the CAC stage. Later, expired copies may be deleted at startup, deleting only UUID-named directories and regular files, not following links.
- **core interface**: `copy_for_opening(snapshot_id) -> OpenedCopy { snapshot, path, sha256, byte_length, can_open, number }`. Errors are the same as `read_snapshot`'s; when it cannot write, it returns `app_data_unavailable`.
  - `number`: the record line number used in the copy's name at the moment the copy was made; null when the name has no number (v20, #140). The UI's open hint shows it and does not recompute it from the current numbering: if relations or works change later and the record line is renumbered, the hint still matches the copy's name (R2-MEM-11).

**Local plain-text preview of historical .docx versions** (#66, v21; core written by D, the command wired by A, the UI wired by B):

- **core interface**: `preview_docx_version(snapshot_id) -> DocxPreview { snapshot, extraction: PreviewText { summary, text } }` (`snapshot.rs`, calls D's `docx::preview_docx_snapshot`).
  - The bytes are taken only from `read_snapshot` (SHA-256 checked); the current file is never read, and there is no fallback. When the snapshot does not exist, is missing or is damaged, it returns `read_snapshot`'s original error.
  - Only the name at capture time is looked at: only an extension of `.docx` (case-insensitive) is handed to `read_docx_cached` (`docx-cache-local-1`); other names return normally with status `unsupported` and the reason in `note`, which is not an error.
  - The text is at most `MAX_MEMORY_TEXT_CHARS` characters; `summary`'s invariants are as in the table above. The cached text of citation fields may be missing or out of date, and is never computed or refreshed; reference manager data that has no marks and has already been flattened may not be recognized. The UI must show these two points (`CACHE_WARNING`, `FLATTENED_WARNING` in D's component).
  - This is the only time a version's text crosses IPC: it is not saved, not logged, not sent to the model, not written to a copy, does not open any app, and does not count as the Memory sending permission. The `Debug` of `DocxPreview` does not show the body.
  - After an authorized folder is revoked, old snapshots can still be previewed, the same as with `copy_for_opening`: what is read is the snapshot in app-data.
- **Command**: `preview_memory_docx({ snapshot_id })` (`memory_commands.rs`, `#[tauri::command(async)]`, does not occupy the UI thread). It uses only the parameter `snapshot_id`, which must be a version ID: passing a path is refused (`invalid_input`), and a missing `snapshot_id` is refused too. Like the other commands that take only an ID, Tauri ignores extra top-level keys (for example `path`); they take no part in any read, so the command never reads a file by path (v22 correction, D103-01; v21 said "extra keys are all refused", which did not match the actual behavior).

The reader is chosen by the extension at capture time: `.docx` uses `docx-cache-local-1`, `.pptx` / `.xlsx` use the preview projection, TXT/MD use `read_text`, and other types return `unsupported`. **Export to the user's folder** (#35, `export.rs`, v13): export a version as a new file in the user's folder.

- **Precondition**: #35 requires Gate 1 PASS before writing user directories; #13 was closed on 10/07. The flow is: the user picks a place in the system save panel, looks at the preview, and only after confirming is anything written. Folders created in the save panel are created by macOS, not written by Traeva.
- **Only Gate 1's primitives are used; no new primitive for writing user directories is added**:
  1. First write the copy in app-data's `opened/<UUID>/`, following "How it is written" above. The file is created with 0666, from which the system subtracts the umask, the same as for files any app creates; permissions are not changed afterwards.
  2. Open the target folder level by level from the authorized root with `open_chain`, not following links; hidden folders, packages and project folders are all refused.
  3. Move it in at once with `move_no_replace` (`RENAME_EXCL`). When the name is taken, the kernel refuses; there is no copy or delete fallback.
  4. After moving in, check `verify_chain` and `confirm_moved` in order, then use `verified_root` to confirm the root is still the original one (`id()` unchanged, equivalent to Organize's `check_after_move`). If any item does not match, return `result_unconfirmed`: do not report success, and do not move the file back. The UI must state separately "it may already have been written; please look in the folder", and must not treat it as an export failure.
  5. On failure, delete the copy in app-data and its UUID directory; on success, delete only the empty UUID directory.
- **Order** (same as `relocate.rs`): first `lock_execution`, then `no_unsettled_action`, and finally `verified_root`. That way a root revoked or replaced while waiting for the lock is never written into. The execution lock is held throughout the move-in.
- **Preview token**: `preview_export` gives a `page_token` that covers the version (ID and SHA-256), the root, the identity of every folder level on the path (dev, ino, birthtime and name) and the file name. `export_version` computes it again and returns `page_outdated` if it differs. `ExportRequest` refuses extra fields (`deny_unknown_fields`).
- **The preview does the same checks as the export**: unresolved Organize operations, crossing disks (comparing the `dev` of app-data and of the target folder, before the copy is written), a revoked root, a taken name. A place the export would certainly refuse is refused already at the preview stage.
- **Limits**: only text versions that `is_text_file_name` recognizes are exported; the name must keep the original extension (case-insensitive) and pass `NewFolderName::parse`; when it does not comply, the message says which rule was broken. The reason is the same as above: a newly written file has no quarantine mark.
- **No database writes; this is an exception the student accepted** (2026-10-10, #104 issuecomment-6101882154): export does not follow "persist the intent first, then do the file side effect, finally record the result". Reason: export only creates a new file and never replaces or moves any existing user file, so no data can be lost; the worst case is the process crashing after the move-in and before the reply, leaving a new file in the user's folder that Traeva has no record of. Exported files belong to the user; Traeva does not track or delete them. The matching requirement: for `result_unconfirmed` the UI must state "it may already have been written to X; please check in the folder; Traeva will not move it away", and must not show it as an export failure.
- **core interface**:
  - `preview_export(snapshot_id, root_id, picked) -> ExportPreview { snapshot, root_id, folder, name, display_path, byte_length, page_token }`, look only, no writing.
  - `export_version(ExportRequest { snapshot_id, root_id, folder, name, page_token }) -> ExportedVersion { snapshot, display_path, sha256, byte_length }`. `folder` is the names inside the root joined with `/`; an empty string means the root itself.

### 4.8 Active-drop auto-organize (A, #168, v26, corrected in v27/v29/v30; rules in organize-spec §13)

After the user explicitly agrees, a file dropped on the Traeva icon is moved automatically when the core judgment of §13.4 is fully satisfied, without showing a confirmation page. **All judgments are in core**; the UI only shows things and collects choices.

- **Code**: `crates/traeva-core/src/auto_drop.rs` and `auto_drop_tests.rs`; `migrations/0010_organize_auto_drop.sql`; `src-tauri/src/drop_commands.rs`, and the receipt of macOS open events in `lib.rs` (`RunEvent::Opened`: dropping on the Dock icon or "Open With"); `src-tauri/tests/drop_ipc.rs`; the TS mirrors and thin API are in `src/features/autodrop/` (the UI is done by the UI polishing session).
- **File type declaration**: `fileAssociations` in `tauri.conf.json` declares `public.data`, role Viewer, `LSHandlerRank` None. So the Dock icon accepts dropped files, but Traeva never becomes the default opener for any type. Only file paths are handed to core; folders and links are always refused.
- **Migration 0010 (two new tables; Organize's original seven tables are not changed)**:
  - `organize_auto_consents`: agreement ID, notice version, target root, target scopes (a JSON array of relative paths in the root; `""` is the root itself), agreement time, revocation time. Core revokes the old one and saves the new one in one transaction, so at most one row is valid at a time.
  - `organize_drop_events`: one row per dropped file: batch and order, file name, received time, root, file, the agreement relied on, plan, execution, result (`received` / `moved` / `already_in_place` / `handed_over` / `stopped` / `not_processed` / `cancelled` / `interrupted`), reason, end time. `moved` always carries the agreement, plan and execution. Only metadata is stored, never body text.
  - **Order of recording** (v30, R1's #182):
    - Before automatic execution, first write the root, the file, the agreement relied on and the plan into this row, with the result still `received`. If they cannot be written, stop (`stopped`), do not call `apply_plan`, and move nothing.
    - After execution, write the result and the execution. When the end record cannot be written, the in-memory state is as usual (the reason followed by "Not recorded"), and the next `drop_queue` writes it later.
    - On restart (before the executor's record check): rows that are still `received`, already have the agreement and plan written, and whose plan's execution is already `committed` (or has been undone since) are changed to `moved` with the execution added; other `received` rows are changed to `interrupted`, with the execution added if there is one, and the result is decided by that execution's record check (organize-spec §7). An execution that has not settled is never recorded as `moved`.
- **Settings**:
  - `auto_drop_settings() -> AutoDropSettingsView { enabled, notice, notice_version, consent_id, agreed_at_ms, target_root_id, scopes: [ScopeView { relative_path, display_path, valid }], problem }`. `enabled` means it is on and the agreement is still valid: the notice is the current version, the target root is usable, and at least one scope is still an existing folder.
  - `set_auto_drop(AutoDropRequest { enable, notice_version, target_root_id, scopes })`: enabling must carry the current `AUTO_DROP_NOTICE_VERSION` (= 1), the target root must be usable, and the scopes must be 1–20 existing folders in this root (from the same bounded folder list analysis uses; protected folders do not count). Turning it off revokes the agreement. A request with extra fields is refused.
  - The target scope is limited to **one** authorized folder: analysis runs on this root's folder list, and the recommended folder must be within some scope (judged by path-segment prefix).
- **Queue** (in memory only, like Organize operations):
  - `receive_drops(paths)`: added in order, writing a `received` row for each file; folders and links go straight to `stopped`.
  - `run_drops()`: processes the files one by one in the background, stopping when user action is needed. Only one runs at a time.
  - `drop_queue() -> DropQueueView { items: [DropItemView { drop_id, file_name, batch_id, received_at_ms, state, automatic, folder_to_authorize, operation_id, plan_id, action_id, moved_to, reason }], running }`. A file being processed stays in place in the list, keeping its `drop_id` and file name, with state `working` (v27). `batch_id` marks the files of the same drop, and `received_at_ms` is the drop time, used to tell apart several drops of the same file (v29; the values are the same as in the drop record; no migration added).
  - `state`: `waiting` / `needs_source_authorization` / `working` / `needs_answer` / `handed_over` / `moved` / `already_in_place` / `stopped` / `not_processed` / `cancelled`. `needs_answer` appears only on files whose `automatic` is true.
  - `action_id` (v27): for `moved` it is this execution; for `stopped`, if it has a value, the move had started but the result was not recorded, so the file may already have moved, and this action's record and recovery check are what count (organize-spec §7); for a `handed_over` file, after the plan is confirmed in the normal flow, `drop_queue` fills that plan and execution into the view and the drop record, with the result still `handed_over`. Changes after the execution (for example an undo) are not written back to the queue; use `get_action` to read the action's current state.
  - `plan_id`: may also have a value for `handed_over` (the agreement was found to have changed before execution). The UI does not execute it directly; it opens the operation and goes through the normal preview as usual.
  - `authorize_drop_source(drop_id)`: permanently authorizes the folder the file is in (same as `authorize_root`; checks such as app-data not overlapping in either direction are unchanged), and the file goes back to `waiting`.
  - `cancel_drop(drop_id)`: cancels this file (and its operation, if any); the later files **in the same drop** are listed as `not_processed`, and other drops are not affected (v29). `waiting`, `needs_source_authorization`, `needs_answer` and `handed_over` (v27) can be canceled; when a `handed_over` file's plan has already been confirmed, the operation refuses to be canceled, this error is returned as is, and nothing is changed. `working` and other finished files are unchanged.
  - To skip only one handed-over file and go on to the next (when auto mode is off): the UI calls `cancel_operation` on its operation (if any), then calls `continue_drops`. The drop record stays `handed_over`.
  - `start_drop_operation(drop_id, target_root_id)`: when auto mode is off, starts a normal operation for a dropped file in an authorized folder; the UI reads, analyzes, previews and confirms as usual.
  - Clarification questions reuse `answer_clarification`; after answering, the UI calls `continue_drops` and the queue keeps running. The order and timing of the two are not restricted: `answer_clarification` sends the post-answer request in the background, and the `continue_drops` round waits for that request to finish before judging (waiting at most twice the model timeout plus 30 seconds; on timeout it switches to the normal flow), and does not send it again (v27).
- **Automatic execution**: after analysis reaches `recommendation_ready`, core checks that the recommended folder needs no new folders and is within scope, then calls the existing `build_plan` with the recommended candidate, confirms that the plan creates no directories and that `can_confirm` is true, **and checks once more right before execution that the agreement is still valid**, then calls the existing `apply_plan`. The executor, journal, recovery and Undo are all reused.
  - In auto mode, when one file stops or goes back to the normal flow (`stopped` / `handed_over`), the later files **in the same drop** are listed as `not_processed`; the queue goes on to process later drops (v29. The v26 implementation also listed later drops as not processed, which did not match organize-spec §13.1 "when several files are dropped at once").
  - When auto mode is off, files are handed to the normal flow one by one; after the UI finishes one, it calls `continue_drops` to process the next.
- **Commands** (`drop_commands.rs`, all `#[tauri::command(async)]`): `get_auto_drop_settings`, `set_auto_drop_settings({ request })`, `get_drop_queue`, `authorize_drop_source({ drop_id })`, `cancel_drop({ drop_id })`, `continue_drops`, `start_drop_operation({ drop_id, target_root_id })`. The command name, handler and `allow-*` permission are kept in sync in all three places. The UI polls `get_drop_queue` at intervals; no event permission is added.

- (v35, #208, for the desktop pet) `DropItemView` gains two fields, computed by core when the queue is read: `needs_user` means this file is now waiting for the user: a folder to authorize, that one question, or a normal flow not yet finished (not yet started, or its operation is neither confirmed, nor finished, nor canceled). When a normal flow ends without a confirmation (already in that folder, given up, this file skipped), the window calls `cancel_operation` to end it. `action_status` is the current state of the execution `action_id` refers to (moves confirmed in the normal flow have it too).

### 4.9 Organize reads the PDF text layer (A, #186, v31; rules in organize-spec §14)

Only Organize reads PDFs, to recommend folders; **Memory does not read PDFs** (`reader::read_text` still returns `Unsupported` for `.pdf`).

- **Code**: `crates/traeva-core/src/pdf_child.rs` (the child process, the capped allocator, the connection into Organize) and `pdf_child_tests.rs`; the reader `pdf.rs` (moved in by G4 from `experiments/pdf-reader`, version `pdf-1`, entry point `pub(crate) fn read_pdf(bytes) -> TextExtraction`); the child-process tests `crates/traeva-core/tests/pdf_child.rs` (including G4's real samples in `tests/fixtures/pdf/`: those with a text layer are read in full, scanned and encrypted ones fall back to a manual pick) and the test program `src/bin/traeva-pdf-text.rs` (`PdfHelper::traeva_with`); the child-process entry and the global allocator in `src-tauri/src/main.rs`; `src-tauri/src/lib.rs` sets `PdfHelper` at startup.
- **Where it connects**: both of Organize's extractions (the observation after a file is chosen, and the reread before sending) go through `organize_extraction(file_name, bytes)` instead: `.pdf` (case-insensitive) is handed to the child process, Word, PowerPoint and Excel are covered in the next item, and other files go through `observe::extract_text` as before. The text read goes through the same excerpting (`observe::excerpt_text`: at most 8,000 Unicode scalar values; when over, the first 6,000 plus the last 2,000).
- **Word, PowerPoint, Excel** (v52, organize-spec v0.16, the student's decision 10/17):
  - `.docx`, `.pptx`, `.xlsx` (`observe::is_office_file_name`, case-insensitive, must have a file name stem) are handed to `office_extraction` in `pdf_child.rs`. It calls, in this process, the `reader::read_text` that Memory and Find use; the scope read and the resource limits all follow §4.4.
  - Excel sheet names are not sent: as in Memory, structure lines are rewritten to `⟦sheet N · id X⟧` (`reader::without_sheet_names`). Hidden slides and sheets are not read. The rewritten text then goes through the same excerpting.
  - When the reader gives `Partial` (PowerPoint always does: only the stored text part is read), the excerpt is also marked `Partial`, with the note written as "Traeva read only part of this file's text. Left out: …", listing the reader's `left_out`. When nothing can be read, it falls back to a manual pick with the reader's own reason.
  - Organize send notice version 7: adds Word, PowerPoint and Excel, and, in the same way as the Memory notice, states clearly what is read from each: Word reads the body (including text Word hides); PowerPoint reads visible slides and speaker notes, plus place lines; Excel reads the cells of visible sheets, including numbers, formula source and the last saved values, and does not send sheet names. Earlier agreements no longer count; a new agreement is needed once. The auto mode agreement notice does not list types, so it is unchanged.
  - prompt `classify-7`: tells the model that lines in ⟦ ⟧ are place labels Traeva added, not the file's text, and that a snippet that is only labels cannot be used as a basis.
  - prompt `classify-8` (v55, organize-spec v0.17): the details in the summary are written in the model's own words, without repeating sentences from the file (at most 8 words or 20 characters in a row), so that the anti-copy check (`ECHO_RUN` = 60) does not refuse it.
  - Cutting the summary when it copies (v56, organize-spec v0.18): the summary is cut where it starts copying 60 or more characters of the original text, with " …" added at the end (when the cut falls in the middle of a word, it backs off to the start of the word), and the recommendation is given as usual; a summary that copies from its very first character is still refused. Reasons, questions, options and new folder names are still refused whole.
  - The app declares that it accepts docx, pptx and xlsx; as with the other types the role is Viewer and `LSHandlerRank` None, so it never becomes the default opener.
- **Child process**:
  - The program is Traeva's own executable; the arguments are `PDF_TEXT_FLAG` (`--traeva-pdf-text`) plus the memory limit in bytes. The environment is cleared, and stderr is discarded.
  - Through stdin, core hands it the bytes that were read twice with matching hashes (at most 20 MiB). The child process receives no path, reads and writes no files, uses no network, and does not access the database or the Keychain.
  - It returns one JSON object on stdout, `{ status: complete|partial|unsupported|failed, text, note }`; extra fields are refused. It does not return the PDF's metadata.
  - Limits: memory `PDF_HEAP_CAP` = 512 MiB (`CappedAlloc` refuses allocations beyond it, and the process then terminates); time `PDF_TIME_LIMIT` = 15 seconds (killed when it runs out); returned content at most 8,000,000 bytes; text at most 1,000,000 characters (`MAX_MEMORY_TEXT_CHARS`); note at most 300 characters.
  - The app itself also has `CappedAlloc` installed, but with no limit; it only counts.
- **How the result is used**:
  - `complete` → `ok` (or `partial` by the excerpting rules); `partial` → usable, with `note` stating the parts left out.
  - `unsupported` / `failed` → no usable text; fall back to a manual pick, nothing sent to the model.
  - Failure to start, timeout, crash, going over the memory limit, malformed returned content, text too long → `failed`, with the note stating the reason in each case; fall back to a manual pick, no retry.
  - `PdfHelper` not set (for example in core tests and IPC tests) → `unsupported`, "Traeva cannot read PDF files here."
- **Send notice**: `settings::NOTICE_VERSION` = 3; the notice states that the excerpt may come from TXT, Markdown or the PDF text layer; version 2 sending permissions are no longer valid.
- **Drops**: `fileAssociations` in `tauri.conf.json` adds `pdf` (still Viewer, `LSHandlerRank` None); §4.8's automatic conditions are unchanged.
- No new commands, migrations or permissions; the shapes of `ExtractionStatus` and `FileView` are unchanged.

**v42: on-device text recognition for images (G4 and A, #37, rules in organize-spec §14.9).**
- Organize only: `observe::is_image_file_name` (`.jpg`, `.jpeg`, `.png`, case-insensitive, must have a stem) takes effect only in the `OcrUse::Allowed` branch of `organize_extraction`, calling `OrganizeService::image_extraction(bytes)`. Memory, Source's registration (`Never`) and Find do not recognize images.
- The parent process first looks at the file header (`pdf_ocr::image_kind`); if it is not PNG or JPEG, it falls back to a manual pick directly, without starting the child process. Then it uses the same child process as §14.8, with `--input image` added to the arguments and the bytes passed through stdin. The 15-second time limit, the 384 MiB soft memory budget, one child process at a time, the ready state, and recognizing the same bytes only once per run are all shared; the result cache and failure records are kept separately by type.
- The child process (`pdf_ocr`'s image module, ImageIO): before decoding, it checks the dimensions from the file header, with limits of 50 million pixels and 20,000 per side; the end of the file must be complete (PNG's IEND, JPEG's FF D9, trailing 0 padding allowed); only the first frame is read; only the EXIF orientation is used to straighten it (WithTransform), and the property dictionary is not read; it is scaled down to within 8 million pixels and drawn onto a white-background grayscale image that is handed to Vision. Transparency, 16-bit and CMYK are all converted, not refused.
- Answer: `partial`; `text` is the recognized lines joined in order with line breaks, without page markers, at least 10 non-whitespace characters and at most 1,000,000 characters. The parent process checks it with `answered_image`; on success the note is always "Read by on-device text recognition from an image; it may contain mistakes.", never the child process's note.
- `NOTICE_VERSION` = 5: the send notice adds "or from a JPEG or PNG image; never the image itself or its location or camera data"; agreements of version 4 and earlier become invalid.
- The drop reason becomes the neutral "Its text was recognized on this Mac and may contain mistakes: check the preview and confirm." (shared by scanned pages and images), never moved automatically (canceled since v47: moved automatically when the other conditions are met, and this reason no longer appears).
- The file declarations in `tauri.conf.json` add `jpg`, `jpeg`, `png` (Viewer, rank None). Dependencies: core's macOS section adds `objc2-image-io` (`=0.3.2`, with only std, CGImageSource and objc2-core-graphics enabled); no new crate is added. No new migration, command or permission.
- Known limits (#265 review): a progressive JPEG close to 50 million pixels, or an interlaced 16-bit PNG, may exceed the 384 MiB soft budget while decoding; the child process is then terminated and readiness is revoked for this run (scanned PDFs also fall back to a manual pick; restored at the next startup). A complete file with data after EOI or IEND (for example trailing data some phones append, Motion Photo) is treated as damaged and falls back to a manual pick.

- **Code**: `crates/traeva-core/src/ocr.rs` (`OcrHelper`, state, preparation, recognition, the kept recognition results and recognized hashes; `ocr_child_main` / `ocr_prepare_main` call `pdf_ocr`'s entry points, `child_footprint` calls `pdf_ocr::process_memory`) and `ocr_tests.rs`; G-OCR's `crates/traeva-core/src/pdf_ocr/` (rendering, Vision, memory monitoring, parent watchdog; outside macOS `without_ocr.rs` answers unsupported); new dependencies `hayro` 0.8.0, and on macOS `objc2` 0.6.4 and `objc2-foundation`, `objc2-core-foundation`, `objc2-core-graphics`, `objc2-vision` (0.3.2, Vision with the `objc2-core-graphics` and `objc2-image-io` features), all under permissive licenses such as MIT / Apache-2.0 / Zlib / BSD-3-Clause / Unlicense, with `THIRD-PARTY-NOTICES.txt` regenerated; the verification test that needs a built app, `tests/ocr_app.rs` (ignored by default; runs only when `TRAEVA_OCR_APP` is set); `run_child` / `Watch` / `Ended` / `ended` in `pdf_child.rs` (starting and watching a child process, shared by the PDF child process and the recognition child process; the PDF child process reads no memory and sets no stop); the child-process tests `tests/ocr_child.rs` and the test program `src/bin/traeva-ocr.rs`; the two entry points in `src-tauri/src/main.rs`; `src-tauri/src/lib.rs` sets `OcrHelper` when the switch is on and prepares in the background, and calls `stop_ocr` on exit; the command `get_ocr_state` (`commands.rs`).
- **Which PDFs are recognized**: only in Organize's reads (`organize_extraction(name, bytes, OcrUse::Allowed)`: the observation after choosing or dropping a file, and the reread before sending). Memory's `start_memory_at`, Source's registration and `register_file` use `OcrUse::Never`; Find uses only the PDF child process. Trigger: the PDF child process returns `unsupported`, and the note starts with one of the reader's two sentences (`ocr::NO_TEXT_LAYER_NOTES`: "No page has a text layer that this reader can use. " and "No page has a text layer; the PDF holds only images and drawings."). `ocr_tests.rs` checks these two sentences against real scanned samples and the source of `pdf.rs`.
- **Child-process interface** (agreed with G-OCR): entry points `ocr_child_main(args: &[String]) -> i32` and `ocr_prepare_main(args: &[String]) -> i32`; `args` is the part after the argument flag. The environment is cleared and stderr is discarded.
  - Preparation child process: `<executable> --traeva-ocr-prepare --parent-pid <app process ID>`, stdin empty. Success = exit code 0 and stdout exactly `{"status":"ready"}` (extra fields refused, at most 1,024 bytes). Time limit `OCR_PREPARE_TIME_LIMIT` = 90 seconds; memory rules as for recognition.
  - Recognition child process: `<executable> --traeva-pdf-ocr --max-pages 3 --dpi 200 --max-pixels 8000000 --parent-pid <app process ID>`. The first three are the **preprocessing budget before recognition**, honored by the child process (`OCR_MAX_PAGES`, `OCR_DPI`, `OCR_MAX_PIXELS`). stdin is the bytes read twice with matching hashes (at most 20 MiB). stdout is one JSON object with the same shape as the PDF child process: `{ status, text, note }`, extra fields refused and wrong types refused too, at most 8,000,000 bytes; text at most 1,000,000 characters; the note shows at most 300 characters.
  - Memory probe: `MemoryProbe` = `fn(pid) -> Option<ProcessMemory>`, `ProcessMemory { footprint_bytes, lifetime_peak_bytes, kernel_lifetime_peak_bytes }` (`pdf_ocr`'s type, `proc_pid_rusage`). The parent process compares `max(footprint_bytes, lifetime_peak_bytes)` with `OCR_MEMORY_LIMIT`. The app uses `child_footprint` = `pdf_ocr::process_memory`.
  - The child process itself: the entry point first sets a 512 MiB counting heap (the same `set_heap_cap` as the PDF child process), checks the arguments (unknown, duplicated, missing a value, or not an approved value → exit code 2), checks that `--parent-pid` is exactly its parent process and looks every 50 ms, exiting if the parent is gone (125). The recognition entry point answers `unsupported` for a PDF with a text layer (even on just one page) before rendering and Vision.
- **Answer format** (R4-OCR-04): recognition counts as successful only when `status` is `partial`; `complete` is treated as malformed. `text` must be 1–3 page segments: each segment's first line is `[Page N]` (N is an integer starting from 1, without leading zeros, each segment larger than the one before, so no repeats; N is this page's position in the PDF), followed by at least one line of recognized text that is not all whitespace, written the same way as by the text layer reader. A segment with only a heading line, page 0, leading zeros, repeats, reversed order, more than 3 segments, text before a heading line, or a heading line followed by other characters are all treated as malformed: `failed`, "Text recognition gave an answer Traeva cannot use.". Success → the extraction is `partial`, `recognized: true`, with the note "Read by on-device text recognition from N scanned page(s); it may contain mistakes." (N is the number of segments, singular or plural by count), followed by the child process's `note` (the number and page numbers of missed pages, the reader's other omissions, at most 300 characters); when that note begins with exactly "OCR read N scanned pages; may contain errors.", this repeated warning is removed (v39, R4-OCR-05, `recognized_note`); this note is cached together with the recognition result. `unsupported` / `failed` → fall back to a manual pick, showing the child process's note.
- **Stopping while running**: `run_child` looks every `OCR_POLL_INTERVAL` = 5 milliseconds. When the child process has ended, it goes to the final check; on receiving a stop (app exit), it terminates the child process; it reads the memory and terminates the child process when it is over `OCR_MEMORY_LIMIT` = 384 MiB or cannot be read; it terminates the child process when it runs over `OCR_TIME_LIMIT` = 15 seconds. 384 MiB is a **soft budget**, not a hard limit: between two reads the child process may briefly exceed it before it is terminated. It is also not the PDF child process's 512 MiB counting heap limit; that one (`PDF_HEAP_CAP`, `CappedAlloc`) is unchanged.
  - **What counts as ended** (R4-OCR-03): `ended(pid)` uses `waitid(P_PID, pid, WEXITED | WNOHANG | WNOWAIT)`, and counts only the `si_code` values `CLD_EXITED`, `CLD_KILLED` and `CLD_DUMPED` as ended. `CLD_STOPPED`, `CLD_CONTINUED` (macOS may report these here too) and "the pid was returned" do not count. A paused (SIGSTOP) child process is still bound by the time limit, the stop flag and the memory check: it is terminated and reaped by `Child::wait`, and the "one at a time" lock is released only after `run_child` returns.
  - **The final check before reaping**: after the child process ends by itself, it is not reaped at first. The parent process reads its memory one last time (the lifetime peak is still readable), checks the stop flag and the time limit again, and only then reaps it with `wait`. Over memory, stopped, or timed out: the answer is discarded. If the memory cannot be read at this point: the answer is discarded and readiness is revoked. The PDF child process goes through the same code, only without the memory check and the stop flag, so its final check is only the time limit: a PDF child process found to have ended only after the time limit is now also treated as a timeout.
  - Tests: `ocr_tests.rs` pauses the preparation and recognition child processes right after they start, and checks that they are terminated at the time limit and reaped (`kill(pid, 0)` returns ESRCH, nothing left behind), and that later preparation and recognition proceed as usual; a normal exit whose last read is over memory, or whose last read fails: the answer is discarded and readiness revoked; a crash. `tests/pdf_child.rs` does the same pause check for the PDF child process.
- **One at a time**: the `OrganizeService.ocr_child` mutex is held for as long as a preparation or recognition **child process** is running. Before the lock is obtained, reading and observing files (including this scanned file itself) goes on as usual and is not blocked; only the next OCR child process has to wait. After a second scanned file obtains the lock, it checks again: if the same bytes have already been recognized, that result is used; if recognition is no longer ready, it falls back to a manual pick.
- **States** (`OcrState`, `snake_case`): `off` / `not_prepared` / `preparing` / `ready` / `failed` / `timed_out` / `cancelled`. `set_ocr_helper(Some)` → `not_prepared` (also clearing the kept results and the recognized hashes). `start_ocr_preparation()` runs only in `not_prepared` and returns the final state: preparation failed, wrong output, memory exceeded or unreadable, lost contact → `failed`; timeout → `timed_out`; `stop_ocr()` → `cancelled`. Recognition timeout, memory exceeded, memory unreadable or lost contact → `failed` (readiness revoked; no more recognition in this run); a crash or malformed returned content does not revoke readiness. `stop_ocr()` sets the stop flag and waits at most 1 second for the running child process to end; after that no new preparation or recognition starts.
- **When not ready**: `preparing` → `unsupported`, with the note `OCR_GETTING_READY_NOTE` ("Text recognition is getting ready (the first time can take about a minute)."); other states → `unsupported`, with the reader's own note, as in v31.
- **The same bytes are recognized only once** (R4-OCR-02):
  - Kept text: the results of the last 8 recognitions (text or failure reason) are kept in memory by SHA-256. The reread before sending, the request after a clarification question and choosing the same file again all use them directly, without starting a child process.
  - Recognized hashes: separately, every SHA-256 recognized in this run and whether it succeeded are recorded, hashes only, no text. For results no longer among those 8: one that failed → `failed`, "Text recognition did not work on this PDF earlier in this run; Traeva tries it again only after it restarts."; one that succeeded → `unsupported`, "This PDF's text was recognized earlier in this run and is no longer kept; choose it again after restarting Traeva.". Neither starts a child process.
  - Neither is written to the database or to files; both are lost when the app exits.
- **Contract fields**: `ExtractionSummary` adds `recognized: bool` (always `false` for other reads), mirrored in `src/features/organize/types.ts`. `context.excerpt` in `analyses.request_meta_json` adds `text_source`: `"ocr"` for recognized text, `"file"` otherwise. The data fields sent to the model are unchanged (prompt and schema unchanged).
- **Send notice**: `settings::NOTICE_VERSION` = 4; the notice's excerpt sources add "text recognized on this Mac from a scanned PDF's pages"; version 3 sending permissions are no longer valid (it is version 4 also when the switch is off). `settings_tests.rs` pins the hash of the version 4 notice.
- **Auto mode (§4.8)** (no longer applies since v47: recognized files are moved automatically when the other conditions are met): `decide_drop` checks `file.extraction.recognized` after the recommendation comes out: if true, `handed_over`, with the reason "Its text was recognized from scanned pages and may contain mistakes: check the preview and confirm."; the operation stops at `recommendation_ready`, with no plan generated and no move.
- **Command**: `get_ocr_state() -> OcrState` (only the main window may call it; `command_names.rs`, `lib.rs` and `capabilities/main-window.json` are in sync); `getOcrState()` in `api.ts`. How the UI shows it is decided by the UI session.
- No new migration; zero writes to authorized folders.

### 4.10 Find: finding files with natural language (A, #198, v32; rules set by the student on 10/12 in #198)

- **Code**: `crates/traeva-core/src/find.rs` and `find_tests.rs`; `list_child_files` in `platform/macos.rs` (lists only names and attributes, does not read content); `pdf_find_text` in `pdf_child.rs` (the same child process, with a time limit of 3 seconds); `find_consent` in `settings.rs`; `src-tauri/src/find_commands.rs`.
- **Scope**: searches only authorized folders that are still valid. Each folder is walked from its handle without following links, by the same rules as Organize's folder list: it does not enter hidden folders, packages or project folders, and does not list symbolic links or special files. Limits: at most 20,000 files, 5,000 folders and 12 levels per search.
- **Four places to match, all on this Mac**: the file name; the description the model wrote during Organize analysis (`summary` in `analyses.result_json`, the latest `validated` one for the same place; if the file has changed since, the result is marked `description_outdated`); the name of the folder it is in; the body (TXT and Markdown with `read_plain_text`, Word, PPT and Excel with Memory's readers, PDF in the child process). Comparison is case-insensitive and removes the combining accents of Latin, Greek and Cyrillic letters.
- **Short forms** (v48, the student's decision 10/16): a word in a file or folder name (split on non-alphanumeric characters) that has at least 4 characters and contains a letter, and is the beginning of a longer word in some wording, also counts as finding that wording, for example the folder `Chem` for `chemistry`, or `Hist` for `world history`. Whole words (`World` for `world history`) and numbers (`2025`) do not count as short forms. Body text and descriptions are not counted this way.
- **Related words** (v48, the student's decision 10/16): for subjects, fields and topics, the model also gives up to 8 related words (`words.related`, one-to-one with `things`): words that files on this topic commonly use but do not necessarily name. When none of a thing's wordings can be found in the file, at least 2 different related words across the four places together also count as a match; a related word must appear at the start of a word (`ion` counts for `ionic`, not for `question`); in text that is not split into words by spaces (Chinese, Japanese, Thai, etc.) it counts wherever it appears, and a word right after such text also counts as being at a word start. When one found related word is only the beginning of another found related word (`mole` and `molecule`, `反应` ("reaction") and `化学反应` ("chemical reaction")), the two count as one, so that one word in the file is not counted twice. `FindMatch.related_words` lists the related words found; `wording` is the first of them, and the snippet is taken where it appears at a word start; on the page this row always reads "Related words it uses", without a place (several words may be in different places).
- **Ranking** (since v48): first by the number of things found by their wordings, then by the total number of things found (including by related words), then by place (file name > description > folder name > body; before v48 folder names ranked after the body), then by the number of related words found, and finally by modified time from newest to oldest.
- **Time** (v51, the student's decision 10/17):
  - Previously `changed` had four levels (today, the past week, a month, a year) and looked only at the modified time.
  - When the question mentions a time, the model gives `when: { newest, oldest, unit }`, meaning from newest to oldest units ago; null when there is no time. The units are minute / hour / day / week / month (30 days) / year (365 days). A little margin is left on both sides, for example "half an hour ago" is 15–60 minutes, and "two days ago" is 1–3 days.
  - No date is sent; the model gives only relative numbers. The range is counted back from the moment of the search; when newest is 0, there is no upper bound.
  - Core checks: newest ≤ oldest, no negative numbers, a known unit; otherwise the whole answer is not used. A range reaching back more than 20 years does not use the time condition (only the time is dropped and the rest is used; the multiplication is checked for overflow first). When newest = oldest, each side is widened by one unit.
  - The model knows neither the date nor the time of day, so when a particular day, week, month or year is mentioned, the range starts at 0 and goes one unit further back: "yesterday" is 0–2 days, "last week" is 0–2 weeks, "last year" is 0–2 years.
  - A file counts if **any one of its three times** falls in the range:
    - The modified time;
    - The time it was put into this folder (APFS's added time): created here, or moved or renamed into it, Traeva's organizing included. Read with `getattrlistat`, reading attributes only, without opening the file, and checked by object;
    - The last opened time macOS records: reading it means opening the file to read an extended attribute, so it is read only for regular files on this Mac, not for files on iCloud.
  - They are looked at in the order above, and the first that matches is written to `FindResult.time_found` (modified / added / opened).
  - `FindResult.added_at_ms` is the time the file was put into the folder, null when it cannot be read; it is filled for both search results and recently opened files.
  - The time shown with a result on the page is the one that matched; with no time condition, the modified time is shown.
- **An authorized folder nested inside another** (v48): the same file (the same object) is walked once from each of the two folders, but it is listed only once, and `coverage` counts it only once. What each walk found is merged onto the first entry (for the same thing, the walk with the better place is taken); descriptions and Memory records are stored under the folder that organized or recorded the file, and are attached when either walk sees them, even if that walk itself had no match.
- **Body**: files over 20 MiB and iCloud files not downloaded to this Mac (only the mark is looked at; a download is never triggered) are not read and are matched by name only. Reading new body text takes at most 10 seconds each time; the text read (or "cannot be read") is cached in memory by the file's object, size, modified time and change time, and used directly by the next search, up to about 32 million characters; it is gone when the app exits.
- **Model**: asked only when the settings, the key and Find's own agreement are all in place. The request is only `{"question": "..."}` (prompt `find-words-3`, through `send_only`; `find-words-1` before v48, `find-words-2` before v51); the answer has `things` (at most 6, each with 1–5 wordings, each wording at most 40 characters), `related` (one group per thing, at most 8 words, each 3–40 characters, or from 2 characters for non-ASCII words; words that do not conform are dropped one by one, without affecting the whole answer), `kinds` and `when`, used only after core has checked them. In all other cases the words of the question itself are used instead (split on non-alphanumeric characters, with common words removed), and `words_by.reason` states why. Before sending and after the answer comes back, it checks again that the agreement is still valid and the search was not canceled; otherwise it does not send, or does not use the answer.
- **Agreement**: `find_consent` in `model-settings.json` (omitted when absent; old files are read as usual), notice version `FIND_NOTICE_VERSION` = 1, separate from Organize's and Memory's agreements; cleared when the provider or model changes.
- **Nothing on disk**: the question, search words and results are kept only in memory (at most 5 searches; when over, old finished searches are dropped first). The original question is taken out of memory as soon as the background run starts and is not kept afterwards. When a new search starts, other searches still in progress are canceled; late results after a cancellation are discarded.
- **No searchable words**: when only common words are left in the question, and there is no file type and no time range (`when` is null), no files are listed (`results` empty, `coverage` null, `words.things` empty).
- **Errors**: when the files could not be searched (for example the database cannot be read), `problem` states the reason and `results` is empty.
- **Recently opened files** (B, #202, the student 10/12): `recent_files()` uses the same walk; for each regular file on this Mac (files on iCloud are not opened) it first checks the object, then opens the file from the folder handle and reads only the extended attribute `com.apple.lastuseddate#PS` (16 bytes: seconds and nanoseconds, little-endian i64); the content is never read. It lists files opened within the last 30 days, by opened time from newest to oldest, at most 20; they are stored as one finished search (`words` null), so opening and showing in Finder still check the object first. `FindResult.opened_at_ms` is also filled in search results. Whether macOS writes this attribute for the various ways of opening a file has only been verified in synthetic tests, and must be checked in a real environment. Command `get_recent_files`.
- **Opening**: the window passes only `find_id` and `result_id`. `find_result_path` opens level by level from the authorized root's handle to that place, checks that it is still the object seen during the search (device, inode, creation time), and only then gives the full path; the Tauri layer uses `/usr/bin/open -R` (show in Finder) or `/usr/bin/open` (open). File moved away or replaced → `file_changed`.
- **Memory records**: when a result's place is exactly where some Memory record's watch is, the record's `chain_id` is attached (open records preferred), so the page can jump to that record.
- **Commands**: `get_find_setup`, `set_find_consent(agree)`, `start_find(question)` (which then runs in the background), `get_find(find_id)`, `cancel_find(find_id)`, `reveal_find_result(find_id, result_id)`, `open_find_result(find_id, result_id)`, `get_recent_files`. Types: `FindSetupView`, `FindView` (`state`: working / done / cancelled, `words`, `words_by`, `results` at most 30, `matched`, `coverage`, `problem`), `FindResult` (v51 adds `added_at_ms`, `time_found`), `FindMatch` (`place`: name / description / folder / text; the body and description come with snippets; `related_words`), `FindCoverage`.
- No new migration, no database writes, zero writes to authorized folders.

## 5. Failure meanings

| Situation | Result |
|---|---|
| Reading a snapshot: the ID is not a valid UUID | `stage: memory`, `code: invalid_input` |
| Reading a snapshot: no such ID | `AppError`, `stage: memory`, `code: unknown_snapshot` |
| Reading a snapshot: the bytes file is missing or cannot be read | `code: snapshot_unavailable`; the file's current content is never used instead |
| Reading a snapshot: the bytes do not match the SHA-256 | `code: snapshot_corrupt`; not used, not repaired |
| Capture: the file record is changed during the read | `stage: observation`, `code: file_changing` (retryable); nothing is written |
| Capture: a copy with the same SHA-256 already exists but its bytes do not match | `code: snapshot_corrupt`; that copy is not overwritten, and no new snapshot is created |
| Capture: app-data cannot be written, or the snapshot directory has been replaced by a symbolic link | `stage: storage`, `code: app_data_unavailable`; neither the user's folders nor the database are changed |
| Listing snapshots: no such `file_id` | `stage: observation`, `code: unknown_file` |
| Listing snapshots: the file is registered but has no snapshots yet | Not an error: an empty list |
| Automatic capture: the file was renamed, moved or deleted | `problem`, `stage: observation`, `code: file_not_found`; not captured, not followed |
| Automatic capture: the original path (same authorized folder, same relative path) now holds a new object Memory has never seen, and the record is open (v45, the student's decision 10/14) | Not an error: `linked_automatically`; it is automatically recorded as the next version of the same work, and the record moves to the new file; no card, no gap recorded, the UI labels it "Linked automatically", and it can be undone (§4.2b) |

**Historical v44 appendix: letting the model look at images (A, #37, rules in organize-spec §14.10).**

The bullets below retain the earlier contract, including restrictions and version numbers that later revisions replaced. For the current contract, see §4.8–§4.9 and [Organize rules](../features/organize-spec.md) §13.4/§14.10. Since v47, OCR-based and image-assisted results may move automatically when the auto-mode agreement and every other execution condition hold. The current Organize send notice is version 7 (v52), and the classification prompt is `classify-8` (v55). The earlier prohibition on automatic moves and notice/prompt versions below are historical.

- Setting: `ImageSending` = `off` (default) / `ask_each_time` / `without_asking`, stored in `image_consent` in `model-settings.json` (off when absent). Valid only for the same provider, model and `IMAGE_NOTICE_VERSION` (1), and Organize's own agreement must also be valid; it becomes invalid when the provider or model changes. `set_image_sending` is only for the main window. Organize's send notice goes up to version 6.
- Reading: `ExtractionSummary.image_input` marks the JPEG/PNG files and the PDFs with no text layer at all that Organize read. When image sending is not off, such files can start analysis even without text; they are never moved automatically.
- When it sends: `without_asking` always sends; `ask_each_time` sends only when `start_analysis` carries `send_image: true` (drops and the pet's panel do not carry it, so they use text only); `off` never sends. When the copy cannot be made: if there is text, only the text is sent; if there is no text, it stops and suggests a manual pick.
- The copy (a G4-style child process, `--output jpeg`): the same recognition child process; for an image only the first frame is taken and straightened by its orientation, for a scanned PDF the first 3 pages. The long side is at most 1568; it is re-encoded as JPEG, removing all APPn, COM and any APP0 that is not pure JFIF, and keeping only the quantization tables, Huffman tables, the baseline frame header and the restart interval. Each is at most 1 MiB, and there are at most 3. The parent process checks the JPEG structure and the frame header dimensions again. Not cached.
- Request: with images, `input` becomes one user message: first the text (the same data as before), then `input_image` (`data:image/jpeg;base64,…`). The data adds `pictures` (I1…), and the model may cite I1–In in `evidence_ids`. The request size limit is relaxed according to the image sizes. The metadata records only the number of `images`; the diagnostic record replaces each image with `[image not kept]`. prompt `classify-5` (since v49 `classify-6`: the summary starts with the file's category and subject, organize-spec v0.15), schema unchanged.
