# OCR core port verification protocol

Recorded before the run, 2026-10-13. Developer verification, not R4 independent acceptance.

Source implementation: #215 `f7923f8f1e0c5055741182e4dd756330cbe7ff72`; main body of the implementation under test `c2854919e7d75d8d27a08bbc2c3871f36fcb20e2`. This round moves the source implementation into an unregistered core module, keeps the original failures, and does not rewrite a second recognizer. main baseline `bebf841070dfcd69080e4b9e02733a8be070d6db`; the five PDF reader source files are identical character for character.

1. Do not modify product shared registration, dependencies, parent scheduling or UI. The port PR only adds the core module and standalone verification files.
2. The new child has a fixed 20 MiB stdin limit; it only outputs a strict `{status,text,note}`. It returns `partial` only when there is usable OCR; the text-layer-only control does not go through Vision and does not claim to be OCR; a failure on any page or overlong text rejects the whole document. Prepare only outputs `{"status":"ready"}` and does not consume stdin.
3. The frozen ordinary samples and truth come from #215 and are used after their hashes are verified; default 3 pages, 200 dpi, 8M pixels, auto language. For the 15 actual PDFs, the detailed reading is compared page by page with the source implementation at the same parameters, for source, text and omissions; the original s09/s10 label failures continue to be cited, and truth must not be changed to turn them into PASS.
4. Unit verification should cover the strict three fields, 20 MiB including its boundary, overlong multi-byte text, mixed-page failure discarding the whole text, output with no OCR, the omission note, and memory None/current/peak. Pixel planning reuses already-tested code; migration differences are checked separately.
5. Create a new hardened-runtime experiment App with ad hoc signing, and verify the signature and system dynamic libraries; inside the bundle, call prepare and the byte child separately with an empty environment. Prepare 90 seconds, recognition 15 seconds, 384 MiB soft budget; record the first run, repeats in new processes, and reaping and recovery after cancellation/short-time-limit stops. Monitoring calls the newly added actual-memory function and records the peak and the stop latency. Evidence from the original bundle must not pass as verification of the new bundle.
6. Any first failure is saved as is; only affected items are re-run. A new bundle ID is on the same Mac that already has Vision, not evidence of a freshly installed device. Real scans, new devices, OS restart, older systems, Intel, formal Tauri wiring and R4 are all untested. No classification model requests, no file uploads.

Addendum before the run: in #218 / `f0f96eee7b7e9b953937be17421ddcafbfd2849d`, A made the existing `set_heap_cap` available crate-wide. As A requested, both child entries set 512 MiB directly; the standalone harness extracts the allocator code verbatim from that file and compiles it, with no separately written algorithm. The port will be based on this new main. Memory sampling keeps the raw kernel peak and also returns max(kernel peak, current footprint), to handle the peak-field lag actually observed; this is not proof of a hard memory cap.

Narrowed-contract addendum (before the new matrix run): per A #211 comment-6140676858, the product entry now allows OCR only when the whole document has no usable text layer; any Text/TextWithOmissions is rejected before render/Vision; the text is rebuilt from at most 3 actual OCR pages. The old detailed migration comparison stays as it was. The entry args require the real parent PID, with an internal watchdog; the recognition resource flags only accept 3/200/8000000. Argument and output unit boundaries are added; signed prepare/cancel/timeout/parent-exit and recovery are re-run, and the fixed sample/text expectations are not relaxed. The earlier first-version 79-item record describes the old output contract and cannot count as passing the new contract. s03-mixed-clear is a single scanned page mixing Chinese and English, with no usable text layer, and is still used for the recovery read.

Minimal output hardening before handoff (before the run): A/R4 require 1–3 Page sections with positive, strictly increasing page numbers and non-empty text. Beyond the real page table being naturally ordered, the output also explicitly rejects 0/repeated/reversed page numbers. If a line of the OCR text, after stripping leading whitespace, starts with the reserved marker `[Page `, the whole document is rejected without rewriting the text, so that a recognized page marker is not mistaken for a protocol boundary. Pure tests cover these counterexamples; the formal metadata's 15 samples + two prepares are re-tested against the same frozen expectations. Prepare, memory and the parent watchdog are unchanged; their full matrix is not mechanically re-run.
