## 2. The delivery mechanism and where the evidence binds directly

Chrome: one specific tab / debugger epoch / Fetch request / IO stream maps to one new acquisition ID.
The data actually returned by IO.read is sent in order to the same persistent native host; the task exclusively creates a new staging file
and keeps holding its descriptor from creation on. Each chunk is written to this descriptor, not by opening the staging path again.
Across tasks, nothing is paired by URL/filename, and no matching file is looked up by hash or time.

Direct acquisition: the request call directly returns the HTTPS response that this task keeps holding; that response's bytes are written to
this task's staging descriptor. It uses the TRAEVA_DIRECT_HTTPS_ACQUISITION namespace.
Chrome takeover uses TRAEVA_CHROME_FETCH_ACQUISITION; in both, chromeDownloadId is null.
The direct request/response handle identifiers are diagnostic IDs generated by this task and do not pose as browser IDs.

Delivery steps:
1. Fixed-length response at EOF; the number of received bytes exactly equals the single Content-Length, and unsupported framing has been rejected.
2. Read a bounded, stable, immutable in-memory snapshot from the continuously held source handle. The hash is used to confirm the snapshot still equals
   the received stream; it is not independent proof linking the source and the object.
3. Inside the already held delivery directory handle, exclusively create the new target with O_EXCL / O_NOFOLLOW; the create call
   returns the target handle directly. The target is a new file object; this fact is recorded explicitly, and it is not described as a move of the original temp object.
4. Write the download quarantine and WhereFroms through the target handle, then write the in-memory snapshot only through this handle.
   At no point is the replaceable staging name renamed, linked or copied.
5. fsync, stable read-back, compare the created object / live target handle / object at the current name, check contents and attributes.
6. Save a local historical receipt. The observation time is recorded at the last object observation; the receipt requires the current path to be re-checked.

Probing showed macOS fclonefileat can clone the held source handle and also refuses to overwrite a target; but the interface does not return a target handle.
To avoid the window of reopening the target after cloning, this version does not use it as a basis for acquisition.
Apple's original interface documentation:
https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/man/man2/clonefile.2

The specific conclusion on safe delivery in this report is: the counterexamples in this run did not make the Writer publish a replaced source object into the delivery directory.
It does not promise that the whole file appears atomically. A write failure/crash can leave this task's own empty, partial or complete file,
which must be marked DELIVERY_UNCERTAIN; "no receipt" must not be used to make a blanket claim that delivery is safe.
Leftovers are not blindly deleted by target name, so as not to delete some other object that replaced it later.

## 4. Remaining windows and unsupported scope

- The target file is visible in the directory from creation until writing finishes, and a fault can leave an incomplete file; atomic publishing and safe cleanup are not yet implemented.
- Object observation and the database/receipt commit are not a cross-file-system transaction. After the last observation, outside actions can still change the name.
  This experiment can only save the historical acquisition fact for the original object; the formal core must register that specific object, rather than later looking up by path
  and binding whichever FileRecord it finds. This integration is not yet implemented; a test receipt must not be treated as the final link.
- When the process ends, the live handle is lost. VERIFIED is not restored from historical inode / birth time / hash / current path alone,
  a task whose stream was already taken is not retried automatically, and a re-download is not passed off as the original task.
- Simultaneous receiving in the same tab is not proven; untested: cross-origin redirects, iframe/worker, automatic attach to new tabs, logged-in downloads,
  blob/data/service-worker, POST, compressed/unknown length/chunked, HTTP/2 and HTTP/3.
- The experiment allowlist has only the synthetic HTTPS origin, within 20 MiB, GET / 200, a single positive CL, no TE, no compression,
  text/plain and simple txt/md attachment names. The filename/declared MIME cannot prove the content is safe.
- Untested: the install/authorization flow for formally released Chrome, public-CA sites, real power loss, disk/file system faults;
  ENOSPC/EIO/attribute errors are injected and do not pose as real disk exhaustion or real physical power loss.
- The directory-check prototype is not the production core's full authorized-path traversal. app-data tampered with by malicious code running as the same user,
  or the browser/extension/native host itself being compromised, is also outside the established trust boundary.

## 5. Permissions, bridging and macOS safety protections

Native Messaging: a real persistent connectNative process, JSON encoded with a native-endian length.
The manifest is only in the current temporary user-data-dir/NativeMessagingHosts, with allowed_origins set to the exact extension ID;
the host checks the caller origin provided by Chrome, a random token on every message, the 0600 config, the message size limit and the command allowlist.
Unauthorized origin / wrong token / unauthorized write / invalid frame / unknown command all have real child-process tests.
There is no loopback Writer port, shell command or arbitrary-path write interface that a web page could call.
It is not identity authentication against arbitrary malicious processes of the same OS user; formal installation, pairing, key rotation and signing await design / R review.
Chrome's official Native Messaging lifecycle and identity parameters:
https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging

debugger: it really attaches and successfully uses Fetch/IO; the official permission warning covers reading and changing website data,
so the save-directory authorization should not be misdescribed as limiting the debugger's own broad capabilities.
This round, CUA reading of the experiment window timed out twice and no actual permission-prompt screenshot was obtained; marked BLOCKED_UI_CAPTURE.
Unpacked loading also does not replace acceptance of the install prompt; this round did not use a silent-debugger argument to hide the prompt.
Official permissions and debugger boundaries:
https://developer.chrome.com/docs/extensions/reference/permissions-list
https://developer.chrome.com/docs/extensions/reference/api/debugger

macOS: the new target gets 0001;...;Traeva-Lab; quarantine and the response URL's WhereFroms written through the held handle,
done before the body is written and read back for checking before completion; the target is 0600 with no execute permission.
The real Chrome fallback file shows 0081;...;Chrome;, which differs from the prototype's marker.
"Has a quarantine attribute" cannot prove that Gatekeeper / XProtect / Safe Browsing behave the same as with Chrome;
the opening flow for risky files was not verified, no downloaded program was run, and system protections were not turned off.
How to set formal security attributes, system behavior and how browser safety checks are preserved: NO-GO / must be tested further.
Apple's public documentation for the URL quarantine property:
https://developer.apple.com/documentation/foundation/urlresourcekey/quarantinepropertieskey

User effort: in future, users need to install/update the extension and understand the debugger/native permissions, explicitly enable takeover, and authorize the save location.
The normal download click can be kept; tab attachment and failure notifications still need product design; this prototype only attaches under manual experiment control.
The necessary system download attributes on newly acquired files and the rule "must not change existing user files / plant hidden source metadata" need to be
explained separately at formal integration. No existing user file or formal permission has been changed now.

## 6. Recommended bounded approach and conditions for releasing integration

Both routes share the same trusted Writer: the Chrome route preferably keeps the click experience; Download with TRAEVA
is the alternative, as an explicit entry for a new task. The latter needs no debugger, but needs new UI, network acquisition and save authorization,
and correct download delivery must not be treated as having completed all product/system safety acceptance.

Recommended: automatic VERIFIED describes only the specific target object of a new trusted acquisition:
valid authorization + independently verified HTTPS/response format + a direct chain from request/stream to the held written object +
complete reception + safe delivery + necessary system protections + exact object registration in core + successful persistence.
This is a proposal awaiting integration; this report does not change the Accepted student material on the student's behalf.

Unsupported before taking the stream → normal Chrome download → keeps the existing candidate, User Confirmed, UNKNOWN.
Failure after taking the stream → explicit failure/uncertain → no promise that Chrome downloaded normally, no automatic repeat request.
Old records, candidates, family members and same-content copies are not upgraded because of this capability.

Before formal integration, at least the following are needed:
1. A checks the descriptor-aware core registration/binding and authorized-path design; C does not modify shared files.
2. R independently re-verifies swap, replacement, rejection, crash and the receipt window on the PR's exact commit, and confirms the leftover policy.
3. Fill in public-CA HTTPS, the actual permission UI, macOS download protection, bridge installation and pairing, and the error-state UI.
4. The student decides, based on the review results, the supported scope and whether to wire it into the formal product; #37's existing wiring is not changed.

So this round can deliver the experiment PR; formal integration is not released for now.
